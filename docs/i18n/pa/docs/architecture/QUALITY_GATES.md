ਰੈਚਟ ਬੇਸਲਾਈਨ ਜਾਂ ਪਾਸ/ਫੇਲ ਨੀਤੀ ਵਰਤਦਾ ਹੈ, ਅਤੇ ਕੀ ਇਹ ਬਿਲਡ ਨੂੰ ਰੋਕਦਾ ਹੈ ਜਾਂ ਸਿਰਫ਼ ਸਲਾਹਕਾਰੀ ਹੈ।

ਸੰਖੇਪ ਸਾਰ ਅਤੇ ਅਲਾਊਲਿਸਟ ਨੀਤੀ ਲਈ, `AGENTS.md` ਵਿੱਚ "ਗੁਣਵੱਤਾ ਗੇਟ ਅਤੇ ਰੈਚਟ" ਭਾਗ
ਦੇਖੋ। ਇਸੇ ਸਿਸਟਮ ਦੇ ਆਲੋਚਨਾਤਮਕ ਮੁਲਾਂਕਣ, ਪਰਿਪੱਕਤਾ ਵਰਗੀਕਰਨ ਅਤੇ ਟੂਲ-ਨਿਰਪੱਖ
ਪੁਨਰ-ਨਿਰਮਾਣ ਯੋਜਨਾ ਲਈ,
[ਗੁਣਵੱਤਾ ਗੇਟ ਪਲੇਬੁੱਕ](../ops/QUALITY_GATE_PLAYBOOK.md) ਦੇਖੋ।

## ਗੇਟ ਇਨਵੈਂਟਰੀ ਅਤੇ ਐਗਜ਼ੀਕਿਊਸ਼ਨ ਪ੍ਰੋਫ਼ਾਈਲ

### ਉਮੀਦਵਾਰ ਦੀ ਮਨਜ਼ੂਰੀ

CI ਅਤੇ Quality Gates ਵਰਕਫ਼ਲੋ ਹਰੇਕ ਇੱਕ ਸਥਿਰ ਫ਼ੈਸਲਾ ਜਾਰੀ ਕਰਦੇ ਹਨ: `Gate / CI` ਅਤੇ
`Gate / Quality`। ਉਨ੍ਹਾਂ ਦੀ ਵਰਜਨਬੱਧ ਦਾਖ਼ਲਾ ਨੀਤੀ ਹਰੇਕ ਅੱਪਸਟ੍ਰੀਮ ਜੌਬ ਨੂੰ
ਲਾਜ਼ਮੀ ਜਾਂ ਸਲਾਹਕਾਰੀ ਵਜੋਂ ਸੂਚੀਬੱਧ ਕਰਦੀ ਹੈ। ਲਾਗੂ ਹੋਣ ਵਾਲਾ ਲਾਜ਼ਮੀ ਜੌਬ ਸਫਲ ਹੋਣਾ ਚਾਹੀਦਾ ਹੈ:
ਗੁੰਮ, ਰੱਦ, ਛੱਡੇ ਗਏ, ਲੰਬਿਤ ਅਤੇ ਅਣਜਾਣ ਨਤੀਜੇ PASS ਸਥਾਪਤ ਨਹੀਂ ਕਰ ਸਕਦੇ। ਇੱਕ ਵੈਧ
ਕੇਵਲ-ਦਸਤਾਵੇਜ਼ ਜਾਂ ਕੇਵਲ-ਕੈਟਾਲੌਗ ਵਰਗੀਕਰਨ ਕੋਡ ਲੇਨ ਨੂੰ ਗੈਰ-ਲਾਗੂ ਬਣਾ ਸਕਦਾ ਹੈ;
ਡਰਾਫਟ PR ਇੱਕ ਸਵੀਕਾਰਿਆ ਹੋਇਆ ਉਮੀਦਵਾਰ ਨਹੀਂ ਹੈ। `hotfix` ਲੇਬਲ ਸਬੂਤ ਦੀ ਲੋੜ ਨੂੰ ਖਤਮ ਨਹੀਂ ਕਰਦਾ।

ਦੋਵੇਂ ਵਰਕਫ਼ਲੋ PR, main/release ਬ੍ਰਾਂਚਾਂ ਉੱਤੇ ਪੁਸ਼, ਮੈਨੁਅਲ ਡਿਸਪੈਚ ਅਤੇ
merge-group ਇਵੈਂਟਾਂ ਨੂੰ ਕਵਰ ਕਰਦੇ ਹਨ। ਪੁਸ਼, ਡਿਸਪੈਚ ਅਤੇ merge-group ਪੂਰੀ ਚੋਣ ਚਲਾਉਂਦੇ ਹਨ। ਫੋਰਕ
ਅਤੇ merge group ਉਹਨਾਂ ਜੌਬਾਂ ਲਈ ਹੋਸਟ ਕੀਤੇ ਰਨਰ ਵਰਤਦੇ ਹਨ ਜੋ ਹੋਰਥਾਂ self-hosted
ਰਨਰ ਚੁਣਦੇ ਹਨ; ਰੋਲਆਉਟ ਤੋਂ ਪਹਿਲਾਂ ਲੋੜੀਂਦੀ ਹੋਸਟ ਕੀਤੀ ਸਮਰੱਥਾ ਦੀ ਪੁਸ਼ਟੀ ਕੀਤੀ ਜਾਣੀ ਚਾਹੀਦੀ ਹੈ।

ਹਰੇਕ JSON ਰਸੀਦ ਚੈੱਕ-ਆਉਟ ਕੀਤੇ SHA, ਵਰਕਫ਼ਲੋ ਰਨ ਅਤੇ ਕੋਸ਼ਿਸ਼ ਦੀ ਪਛਾਣ ਕਰਦੀ ਹੈ।
CLI ਚੈੱਕਆਉਟ/ਇਵੈਂਟ SHA ਦੇ ਬੇਮੇਲ ਨੂੰ ਅਸਵੀਕਾਰ ਕਰਦਾ ਹੈ। ਵਰਕਫ਼ਲੋ ਟੈਸਟ ਨੀਤੀ ਦੀ ਮੈਂਬਰਸ਼ਿਪ ਨੂੰ
ਫ਼ੈਸਲਾ ਜੌਬ ਦੀ `needs` ਸੂਚੀ ਨਾਲ ਜੋੜਦੇ ਹਨ, ਤਾਂ ਜੋ ਕੋਈ ਨਵੀਂ ਜਾਂ ਹਟਾਈ ਗਈ ਲੇਨ ਚੁੱਪਚਾਪ ਗਾਇਬ ਨਾ ਹੋ ਸਕੇ।
ਰਸੀਦਾਂ ਆਪਣੇ ਵਰਕਫ਼ਲੋ ਨੂੰ ਕਵਰ ਕਰਦੀਆਂ ਹਨ, ਪ੍ਰਕਾਸ਼ਨ, ਡਿਪਲੌਇਮੈਂਟ ਜਾਂ ਕਿਸੇ ਮੌਜੂਦਾ
ਸਲਾਹਕਾਰੀ ਸਕੈਨਰ ਦੇ ਅੰਦਰੂਨੀ ਹਿੱਸਿਆਂ ਨੂੰ ਨਹੀਂ। ਬ੍ਰਾਂਚ ਨਿਯਮਾਂ ਵਿੱਚ ਦੋਵੇਂ ਚੈੱਕ ਨਾਮ ਸਰਗਰਮ ਕਰਨਾ
ਇੱਕ ਵੱਖਰੀ ਪ੍ਰਸ਼ਾਸਕੀ ਤਬਦੀਲੀ ਹੈ; ਇਹਨਾਂ ਜੌਬਾਂ ਨੂੰ ਸ਼ਾਮਲ ਕਰਨਾ ਆਪਣੇ ਆਪ ਵਿੱਚ ਕਿਸੇ ਬ੍ਰਾਂਚ ਦੀ ਰੱਖਿਆ ਨਹੀਂ ਕਰਦਾ।

### ਸਟੈਟਿਕ ਸਕੈਨ ਇਨਵੈਂਟਰੀ

ਵਰਜਨਬੱਧ npm-alias ਇਨਵੈਂਟਰੀ ਅਤੇ ਸਟੈਟਿਕ-ਸਕੈਨ ਮੈਂਬਰਸ਼ਿਪ
`config/quality/gate-manifest.json` ਵਿੱਚ ਮੌਜੂਦ ਹਨ। ਸਕ੍ਰਿਪਟ ਨਾਮਾਂ ਅਤੇ ਸਹੀ ਕਮਾਂਡਾਂ ਨੂੰ
`package.json` ਨਾਲ ਪ੍ਰਮਾਣਿਤ ਕਰਨ ਲਈ `npm run check:gate-manifest` ਚਲਾਓ; ਜੋੜ, ਹਟਾਉਣ ਅਤੇ
ਕਮਾਂਡ ਡ੍ਰਿਫ਼ਟ ਸਥਾਨਕ ਹੁੱਕ ਅਤੇ CI ਵਿੱਚ ਤਬਦੀਲੀ-ਵਰਗੀਕਰਨ ਜੌਬਾਂ ਦੋਵਾਂ ਨੂੰ ਅਸਫਲ ਕਰਦੇ ਹਨ।
ਇੱਕ alias ਕੋਈ ਵਰਕਫ਼ਲੋ ਜੌਬ, ਮੈਟ੍ਰਿਕਸ ਇੰਸਟੈਂਸ ਜਾਂ ਟੈਸਟ ਕੇਸ ਨਹੀਂ ਹੈ: ਇਹਨਾਂ ਗਿਣਤੀਆਂ ਨੂੰ
ਪਰਸਪਰ ਬਦਲਣਯੋਗ ਵਜੋਂ ਪੇਸ਼ ਨਹੀਂ ਕੀਤਾ ਜਾਣਾ ਚਾਹੀਦਾ।

ਚੁਣੇ ਹੋਏ aliases ਨੂੰ ਚਲਾਏ ਬਿਨਾਂ ਜਾਂਚਣ ਲਈ `npm run quality:scan -- --list` ਜਾਂ
`npm run quality:scan:fast -- --list` ਵਰਤੋ।
ਰਨਰ npm ਐਂਟਰੀਪੁਆਇੰਟ ਨੂੰ ਸੱਦਦਾ ਹੈ, ਇਸ ਲਈ ਇਸ ਦਾ ਰਨਟਾਈਮ (ਜਿੱਥੇ ਸੰਰਚਿਤ ਹੋਵੇ, ਉੱਥੇ Bun ਸਮੇਤ)
ਬਰਕਰਾਰ ਰਹਿੰਦਾ ਹੈ। ਮੈਨੀਫੈਸਟ ਉਹਨਾਂ ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਤੋਂ ਬਾਹਰ ਦੇ aliases ਨੂੰ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਸੱਦੇ ਗਏ ਵਜੋਂ
ਦਰਜ ਕਰਦਾ ਹੈ, ਅਤੇ ਕੇਵਲ-ਪੜ੍ਹਨ ਵਾਲੇ ਸਕੈਨ ਪ੍ਰੋਫ਼ਾਈਲਾਂ ਵਿੱਚ ਰੱਖ-ਰਖਾਅ ਕਮਾਂਡਾਂ ਮਨਾਹੀ ਹਨ।

ਇਹ ਪ੍ਰੋਫ਼ਾਈਲ ਸਿਰਫ਼ ਸਟੈਟਿਕ ਸਕੈਨ ਨੂੰ ਕਵਰ ਕਰਦੇ ਹਨ। ਇਹ ਪ੍ਰੋਡਕਟ ਟੈਸਟਾਂ,
ਕਵਰੇਜ, ਪੈਕੇਜਿੰਗ, ਬਾਹਰੀ ਚੈੱਕਾਂ ਜਾਂ ਕਿਸੇ ਉਮੀਦਵਾਰ ਦੀ ਪੂਰੀ ਰਿਲੀਜ਼ ਸਵੀਕ੍ਰਿਤੀ ਨੂੰ ਪ੍ਰਮਾਣਿਤ ਨਹੀਂ ਕਰਦੇ।
ਵਰਕਫ਼ਲੋ ਦਾਖ਼ਲਾ ਲਿੰਕ ਕੀਤੇ `config/quality/admission-policy.json` ਅਤੇ
`scripts/quality/admission-verdict.mjs` ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ। Release-observer ਪ੍ਰੋਫ਼ਾਈਲ ਵੱਖਰੇ ਰਹਿੰਦੇ ਹਨ;
ਉਹਨਾਂ ਦੇ ਲਾਗੂ ਚੈੱਕਾਂ ਅਤੇ ਰਸੀਦਾਂ ਦੀ ਸੁਤੰਤਰ ਤੌਰ 'ਤੇ ਜਾਂਚ ਕਰੋ। ਹੇਠਾਂ ਦਿੱਤੀ ਲਿਖਤੀ
ਇਨਵੈਂਟਰੀ ਇੱਕ ਹਵਾਲਾ ਹੈ, ਇਸ ਗੱਲ ਦਾ ਸਬੂਤ ਨਹੀਂ ਕਿ ਕੋਈ ਗੇਟ ਵਾਸਤਵ ਵਿੱਚ ਚੱਲਿਆ ਸੀ।

ਸਕ੍ਰਿਪਟਾਂ `scripts/check/` (ਨੀਤੀ ਗੇਟ) ਅਤੇ `scripts/quality/` (ਰੈਚਟ ਇੰਜਣ) ਦੇ ਅਧੀਨ ਮੌਜੂਦ ਹਨ।
CI ਲਈ ਪ੍ਰਮਾਣਿਕ ਸਰੋਤ `.github/workflows/ci.yml` ਹੈ।

### Release PR ਫਾਸਟ-ਪਾਥ (`quality.yml`)

`.github/workflows/quality.yml` main/release PR, ਸੁਰੱਖਿਅਤ-ਬ੍ਰਾਂਚ ਪੁਸ਼ਾਂ,
ਡਿਸਪੈਚ ਅਤੇ merge group ਉੱਤੇ CI ਦੀ ਪੂਰਤੀ ਕਰਦਾ ਹੈ। PR ਪਾਥ-ਫਿਲਟਰ ਕੀਤੇ ਤੇਜ਼ ਚੈੱਕ ਵਰਤਦੇ ਹਨ। ਸਥਾਈ ਤੌਰ 'ਤੇ
ਅਸਮਰੱਥ ਕੀਤਾ ਡੁਪਲੀਕੇਟ ਬਿਲਡ ਹਟਾ ਦਿੱਤਾ ਗਿਆ ਸੀ; ਅਸਲ ਬਿਲਡ/ਪੈਕੇਜ/ਬੂਟ ਚੈੱਕ CI ਵਿੱਚ ਮੌਜੂਦ ਰਹਿੰਦੇ ਹਨ।

#### ਭੁੱਲੇ ਹੋਏ sibling tests ਦੀ ਰਿਪੋਰਟ

`npm run check:forgotten-sibling-tests` test-impact ਮੈਪ ਦੇ ਪਿੱਛੇ ਵਾਲੇ import resolver ਦੀ ਮੁੜ ਵਰਤੋਂ ਕਰਦਾ ਹੈ।
ਹਰੇਕ ਬਦਲੇ ਹੋਏ production ਮੌਡਿਊਲ ਲਈ, ਜਦੋਂ ਸੰਭਾਵੀ
ਟੈਸਟ pull-request diff ਵਿੱਚ ਮੌਜੂਦ ਨਹੀਂ ਹੁੰਦਾ, ਤਾਂ ਇਹ ਨਿਰਧਾਰਤ
`changed module/symbol -> static consumer -> candidate sibling test` ਚੇਨਾਂ ਦੀ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ।
ਕਿਸੇ ਵੀ ਬਲੌਕਿੰਗ ਰੋਲਆਉਟ ਤੋਂ ਪਹਿਲਾਂ ਕੈਲੀਬ੍ਰੇਸ਼ਨ ਲਈ Markdown ਸੰਖੇਪ ਅਤੇ JSON ਨਤੀਜੇ ਨੂੰ
`forgotten-sibling-tests` ਵਰਕਫ਼ਲੋ ਆਰਟੀਫੈਕਟ ਵਜੋਂ ਸੰਭਾਲਿਆ ਜਾਂਦਾ ਹੈ।

Barrel ਮੁੜ-ਨਿਰਯਾਤ ਅਤੇ ਡਾਇਨਾਮਿਕ ਇੰਪੋਰਟ ਸਿਰਫ਼ ਰਿਜ਼ੋਲਿਊਸ਼ਨ ਡਾਇਗਨੋਸਟਿਕ ਹਨ; ਇਹ ਕਦੇ ਵੀ
ਰੋਕੂ ਨਤੀਜਾ ਨਹੀਂ ਬਣਾਉਂਦੇ। ਸਮੀਖਿਆ ਕੀਤੇ ਅਪਵਾਦ
`config/quality/forgotten-sibling-allowlist.json` ਵਿੱਚ ਮੌਜੂਦ ਹਨ। ਹਰ ਐਂਟਰੀ ਵਿੱਚ ਉਪਭੋਗਤਾ ਅਤੇ ਉਮੀਦਵਾਰ
ਟੈਸਟ ਦਾ ਨਾਮ ਹੋਣਾ, ਇੱਕ ਖ਼ਾਸ ਤਰਕ ਦੇਣਾ, ਅਤੇ ਕਿਸੇ GitHub issue ਜਾਂ pull request ਨਾਲ ਲਿੰਕ ਕਰਨਾ ਲਾਜ਼ਮੀ ਹੈ। ਗਲਤ ਬਣਤਰ ਵਾਲੀਆਂ ਐਂਟਰੀਆਂ
ਬੰਦ ਸਥਿਤੀ ਵਿੱਚ ਅਸਫਲ ਹੁੰਦੀਆਂ ਹਨ। ਅਪਵਾਦ ਮਿਟਾਏ ਗਏ ਉਮੀਦਵਾਰ ਟੈਸਟ ਜਾਂ `.skip`/`.todo` ਜੋੜਨ ਵਾਲੇ diff ਨੂੰ ਦਬਾ ਨਹੀਂ ਸਕਦੇ;
assertion ਨੂੰ ਕਮਜ਼ੋਰ ਕਰਨਾ ਅਤੇ ਹੋਰ masking ਸੁਤੰਤਰ ਤੌਰ 'ਤੇ ਰੋਕੂ
`check:test-masking` gate ਦੇ ਅਧੀਨ ਰਹਿੰਦੇ ਹਨ।

URL ਕਾਪੀ ਕਰਕੇ ਹੇਠਾਂ ਪੇਸਟ ਕਰੋ" ਦੱਸਣ ਵਾਲਾ ਟੈਕਸਟ ਹੀ ਰਿਹਾ — ਇੱਕ ਅਜਿਹਾ flow ਜੋ ਉਸ provider ਲਈ ਪੂਰਾ ਨਹੀਂ ਹੋ ਸਕਦਾ। ਇਹ
#8463 ਤੱਕ ਨਜ਼ਰ ਨਹੀਂ ਆਇਆ ਕਿਉਂਕਿ:

- `sync-ui-keys` ਸਿਰਫ਼ ਉਹ keys backfill ਕਰਦਾ ਹੈ ਜੋ **ਗੈਰ-ਮੌਜੂਦ** ਹਨ, ਉਹ ਨਹੀਂ ਜੋ **ਪੁਰਾਣੀਆਂ** ਹਨ;
- `check-ui-keys-coverage` key ਦੀ _ਮੌਜੂਦਗੀ_ ਗਿਣਦਾ ਹੈ, ਇਸ ਲਈ ਪੁਰਾਣੇ ਅਨੁਵਾਦ ਨੂੰ covered ਵਜੋਂ ਗਿਣਿਆ ਜਾਂਦਾ ਹੈ;
- `check-translation-drift` `docs/i18n/<locale>/**.md` documentation mirrors ਨੂੰ track ਕਰਦਾ ਹੈ —
  ਇਹ ਕਦੇ ਵੀ `src/i18n/messages/*.json` ਨਹੀਂ ਪੜ੍ਹਦਾ। 2026-09 re-sync ਤੋਂ ਬਾਅਦ job `docs-sync-strict` ਵਿੱਚ blocking: ਇੱਕ core doc ਸੰਪਾਦਿਤ ਕਰੋ → `npm run i18n:run -- --files=<doc>` (section-level, ਸਸਤਾ)।

**Diff-ਜਾਗਰੂਕ, baseline-ਸਮਰਥਿਤ ਨਹੀਂ।** ਇਹ merge base ਉੱਤੇ ਮੌਜੂਦ `en.json` ਦੀ ਤੁਲਨਾ
working tree ਨਾਲ ਕਰਦਾ ਹੈ; ਹਰ ਉਸ key ਲਈ ਜਿਸਦਾ ਅੰਗਰੇਜ਼ੀ ਮੁੱਲ ਬਦਲਿਆ ਹੈ, ਕੋਈ ਵੀ locale ਜਿਸ ਵਿੱਚ
ਅਜੇ ਵੀ ਨਾ-ਛੇੜਿਆ ਅਨੁਵਾਦ ਮੌਜੂਦ ਹੈ, ਪੁਰਾਣਾ ਮੰਨਿਆ ਜਾਂਦਾ ਹੈ। ਇਹ ਜਾਣ-ਬੁੱਝ ਕੇ **ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਕਰਜ਼ੇ ਨੂੰ ਜਮਾਂ ਰੱਖਦਾ ਹੈ** — ਇੱਕ diff
ਇਹ ਨਹੀਂ ਦੱਸ ਸਕਦਾ ਕਿ ਲੰਮੇ ਸਮੇਂ ਤੋਂ ਮੌਜੂਦ ਅਨੁਵਾਦ ਕਿਸ ਪੁਰਾਣੇ ਅੰਗਰੇਜ਼ੀ ਪਾਠ ਤੋਂ ਆਇਆ ਸੀ, ਇਸ ਲਈ gate
ਸਿਰਫ਼ ਉਸੇ ਨੂੰ ਪਰਖਦਾ ਹੈ ਜਿਸਨੂੰ ਮੌਜੂਦਾ ਤਬਦੀਲੀ ਛੂੰਹਦੀ ਹੈ। ਵਿਕਲਪ (ਹਰ-key hash baseline) ਲਈ
ਲਗਭਗ 600 KB ਦੀ generated file ਲੋੜੀਂਦੀ ਹੋਵੇਗੀ, ਜੋ ਸਭ ਤੋਂ ਵੱਡੇ ਮੌਜੂਦਾ baseline ਤੋਂ 3× ਵੱਡੀ ਹੈ ਅਤੇ ਹਰ i18n PR ਉੱਤੇ ਬਦਲੇਗੀ।

ਇਸਨੂੰ ਸੰਤੁਸ਼ਟ ਕਰਨ ਦੇ ਦੋ ਤਰੀਕੇ ਹਨ:

1. ਪ੍ਰਭਾਵਿਤ ਅਨੁਵਾਦਾਂ ਨੂੰ ਅੱਪਡੇਟ ਕਰੋ, ਜਾਂ
2. ਉਨ੍ਹਾਂ ਨੂੰ `__MISSING__:<new english>` ਉੱਤੇ ਸੈੱਟ ਕਰੋ — ਫਿਰ runtime ਸਹੀ ਕੀਤਾ ਅੰਗਰੇਜ਼ੀ ਪਾਠ ਦਿੰਦਾ ਹੈ
   (`src/i18n/request.ts::deepMergeFallback`, #7258) ਅਤੇ key ਅਨੁਵਾਦ ਲਈ ਕਤਾਰ ਵਿੱਚ ਚਲੀ ਜਾਂਦੀ ਹੈ।

ਜੇ string ਦਾ **ਅਰਥ** ਬਦਲਿਆ ਹੈ, ਤਾਂ **key ਦਾ ਨਾਮ ਬਦਲਣ** ਨੂੰ ਤਰਜੀਹ ਦਿਓ: ਇੱਕ ਨਵੀਂ key
ਪੁਰਾਣਾ ਅਨੁਵਾਦ ਵਿਰਾਸਤ ਵਿੱਚ ਨਹੀਂ ਲੈ ਸਕਦੀ। #8463 ਨੇ ਇਹੀ pattern ਵਰਤਿਆ ਸੀ।

```bash
npm run i18n:check-value-drift          # ਸਖ਼ਤ (ਜੋ CI ਚਲਾਉਂਦਾ ਹੈ)
npm run i18n:check-value-drift:warn     # ਸਿਰਫ਼ ਰਿਪੋਰਟ
BASE_REF=origin/release/vX.Y.Z npm run i18n:check-value-drift
```

ਜਦੋਂ base catalog ਪੜ੍ਹਿਆ ਨਹੀਂ ਜਾ ਸਕਦਾ (base ref ਤੋਂ ਬਿਨਾਂ shallow
clone), ਤਾਂ `SKIP reason=base-unresolved` ਨਾਲ 0 ਉੱਤੇ exit ਕਰਦਾ ਹੈ, ਜੋ `check-openapi-breaking` ਦੇ ਵਿਹਾਰ ਨੂੰ ਦਰਸਾਉਂਦਾ ਹੈ।

`check:dead-code` ਲਈ, ਗੇਟ HEAD ਦੀ merge-base ਨਾਲ ਤੁਲਨਾ **ਸਿਰਫ਼ ਉਨ੍ਹਾਂ ਫ਼ਾਈਲਾਂ ਤੱਕ ਸੀਮਿਤ ਰੱਖ ਕੇ ਕਰਦਾ ਹੈ ਜਿਨ੍ਹਾਂ ਨੂੰ PR ਨੇ
ਛੂਹਿਆ ਹੈ** (`scripts/check/newCodeMode.mjs`: merge-base ਨੂੰ ਇੱਕ ਅਸਥਾਈ
`git worktree` ਵਿੱਚ ਸਾਕਾਰ ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ESLint/knip ਉੱਥੇ ਅਤੇ HEAD ਉੱਤੇ ਚਲਾਏ ਜਾਂਦੇ ਹਨ, ਅਤੇ ਪ੍ਰਤੀ-ਫ਼ਾਈਲ ਗਿਣਤੀਆਂ ਦਾ ਅੰਤਰ ਕੱਢਿਆ ਜਾਂਦਾ ਹੈ):

- **ਰੋਕਣ ਵਾਲਾ** — PR ਨੇ ਆਪਣੀਆਂ ਬਦਲੀਆਂ ਫ਼ਾਈਲਾਂ ਵਿੱਚ cyclomatic/cognitive ਉਲੰਘਣਾਵਾਂ ਜਾਂ dead exports ਜੋੜੇ
  (ਲੌਗ ਵਿੱਚ `complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=`);
- **ਸਲਾਹਕਾਰੀ** — ਫ਼੍ਰੀਜ਼ ਕੀਤੀ ਬੇਸਲਾਈਨ ਦੇ ਮੁਕਾਬਲੇ ਕੁੱਲ ਗਲੋਬਲ ਮੁੱਲ। ਵਿਰਾਸਤ ਵਿੱਚ ਮਿਲਿਆ drift ਕਿਸੇ
  ਬੇਕਸੂਰ PR ਨੂੰ ਕਦੇ ਅਸਫਲ ਨਹੀਂ ਕਰਦਾ; ਰਿਲੀਜ਼ ਮਿਲਾਣ ਦੌਰਾਨ drift ਨੂੰ ਮੁੜ ਫ਼੍ਰੀਜ਼ ਕੀਤਾ ਜਾਂਦਾ ਹੈ ਅਤੇ headroom ਜੌਬ ਦੁਆਰਾ ਨਿਗਰਾਨੀ ਕੀਤੀ ਜਾਂਦੀ ਹੈ।

`check:file-size` ਆਪਣੇ ਨਿਯਮਾਂ ਅਨੁਸਾਰ base ref ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ (`scripts/check/check-file-size.mjs`, #8522):
ਇਹ ਟ੍ਰੀ ਵਿੱਚ ਹਰ ਸਰੋਤ ਅਤੇ ਟੈਸਟ ਫ਼ਾਈਲ ਦੀ ਜਾਂਚ ਕਰਦਾ ਹੈ, `git show` ਨਾਲ PR base ਉੱਤੇ ਹਰੇਕ ਦੀ ਲਾਈਨ ਗਿਣਤੀ ਪੜ੍ਹਦਾ ਹੈ,
ਅਤੇ ਕਿਸੇ ਫ਼ਾਈਲ ਨੂੰ ਕੇਵਲ ਉਦੋਂ ਅਸਫਲ ਕਰਦਾ ਹੈ ਜਦੋਂ ਉਹ ਆਪਣੀ ਬੇਸਲਾਈਨ ਹੱਦ
(`frozen` / `testFrozen`, ਜਾਂ ਬੇਸਲਾਈਨ ਤੋਂ ਬਾਹਰਲੀ ਫ਼ਾਈਲ ਲਈ `cap` / `testCap`) ਅਤੇ ਆਪਣੇ base
ਆਕਾਰ ਵਿੱਚੋਂ ਵੱਡੇ ਮੁੱਲ ਤੋਂ ਅੱਗੇ ਵਧਦੀ ਹੈ। ਇਸ ਲਈ base ਉੱਤੇ ਪਹਿਲਾਂ ਹੀ drift ਹੋ ਚੁੱਕੀ ਫ਼ਾਈਲ ਕਦੇ ਵੀ ਕਿਸੇ ਬੇਕਸੂਰ PR ਨੂੰ ਅਸਫਲ ਨਹੀਂ ਕਰਦੀ।

`check:boundary:ratchet` ਆਪਣੇ ਇਕੱਲੇ ਅੰਕ ਉੱਤੇ ਵੀ ਇਹੀ ਨਿਯਮ ਲਾਗੂ ਕਰਦਾ ਹੈ
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): PR ਇਵੈਂਟਾਂ ਉੱਤੇ
`quality.yml` ਦੇ ਫਾਸਟ-ਗੇਟ ਅਤੇ `ci.yml` ਦੀ lint ਜੌਬ ਦੋਵੇਂ PR ਦਾ ਬੇਸ SHA ਪਾਸ ਕਰਦੇ ਹਨ, ਬੇਸ commit ਨੂੰ
`git archive` ਐਕਸਪੋਰਟ ਤੋਂ ਮਾਪਿਆ ਜਾਂਦਾ ਹੈ, ਅਤੇ PR ਕੇਵਲ ਤਦੋਂ ਫੇਲ੍ਹ ਹੁੰਦਾ ਹੈ ਜਦੋਂ ਇਸ ਦੀ `open-sse → src` edge
ਗਿਣਤੀ `metrics.boundaryOpenSseToSrc` ਅਤੇ ਬੇਸ ਉੱਤੇ ਮੌਜੂਦ ਗਿਣਤੀ ਵਿੱਚੋਂ ਵੱਡੀ ਗਿਣਤੀ ਤੋਂ ਵੱਧ ਹੋਵੇ। ਸੀਮਾ ਤੋਂ
ਵੱਧ ਬੇਸ ਡ੍ਰਿਫਟ ਦੀ ਰਿਪੋਰਟ (`base drift herdado`) ਕੀਤੀ ਜਾਂਦੀ ਹੈ, ਪਰ ਇਹ ਕਦੇ ਵੀ ਕਿਸੇ ਬੇਕਸੂਰ PR ਨੂੰ ਫੇਲ੍ਹ ਨਹੀਂ ਕਰਦੀ;
push → main ਲਈ ਪੂਰਨ ਸੀਮਾ ਬਰਕਰਾਰ ਰਹਿੰਦੀ ਹੈ, ਅਤੇ ਹੱਲ ਨਾ ਹੋ ਸਕਣ ਵਾਲਾ ਬੇਸ SHA ਚੇਤਾਵਨੀ ਸਮੇਤ ਉਸੇ ਸੀਮਾ ਉੱਤੇ ਵਾਪਸ ਆ ਜਾਂਦਾ ਹੈ।

`workflow_dispatch` ਰਨ, release-green ਸਵੀਪ ਅਤੇ nightly headroom ਜੌਬ ਕੋਲ ਕੋਈ PR ਬੇਸ ਨਹੀਂ ਹੁੰਦਾ
ਅਤੇ ਉਹ ਪੂਰਨ (ਗਲੋਬਲ) ਤੁਲਨਾ ਬਰਕਰਾਰ ਰੱਖਦੇ ਹਨ। ਕਵਰੇਜ, ਡੁਪਲੀਕੇਸ਼ਨ ਅਤੇ type-coverage ਫਿਲਹਾਲ ਗਲੋਬਲ ਹੀ
ਰਹਿੰਦੇ ਹਨ (ਉਨ੍ਹਾਂ ਦੇ ਟੂਲ ਘੱਟ ਲਾਗਤ ਨਾਲ ਪ੍ਰਤੀ-ਫਾਈਲ diff ਤਿਆਰ ਨਹੀਂ ਕਰਦੇ) — ਇਹ ਵੀ ਇਸੇ ਤਰ੍ਹਾਂ ਦੇ ਇਲਾਜ ਲਈ ਉਮੀਦਵਾਰ ਹਨ।

**v4.0 ਉੱਤੇ ਪੜਾਅ ਨੂੰ ਸਮਾਪਤ ਕਰਨਾ (LTS = ਪਹਿਲਾਂ ਨਾਲੋਂ ਹੋਰ ਸਖ਼ਤ, "ਮੁੜ ਆਮ ਹਾਲਤ ਵਿੱਚ" ਨਹੀਂ)**

1. ਸ਼ੁੱਧ `release/v4.0.0` tip ਉੱਤੇ: ਰਿਕਾਰਡ ਲਈ `npm run quality:headroom --json`, ਫਿਰ
   `npm run quality:ratchet -- --update`, `check:file-size --update`,
   `check:complexity-ratchets --update`, `check:dead-code --update`, ਹਰ typecheck ਗੇਟ ਦਾ
   `--update` — ਹਰੇਕ ਬੇਸਲਾਈਨ ਮਾਪੇ ਗਏ ਮੁੱਲ ਤੱਕ ਘਟ ਜਾਂਦੀ ਹੈ।
2. `quality-baseline.json` ਵਿੱਚੋਂ `_policy` ਮਿਟਾਓ (`--require-tighten` ਅਤੇ nightly
   ਬੈਂਕਿੰਗ ਨੂੰ ਮੁੜ ਸਰਗਰਮ ਕਰਦਾ ਹੈ), `check-openapi-coverage.mjs` ਵਿੱਚ `THRESHOLD = 36` (ਜਾਂ ਇਸ ਤੋਂ ਵੱਧ) ਮੁੜ ਸਥਾਪਤ ਕਰੋ।
3. ਜਿੱਥੇ ਮੋਡੀਊਲਰਾਈਜ਼ੇਸ਼ਨ ਦਾ ਲਾਭ ਮਿਲਿਆ ਹੈ, ਉੱਥੇ ਮਾਪੇ ਗਏ ਮੁੱਲ ਤੋਂ ਵੀ ਅੱਗੇ ਸਖ਼ਤੀ ਕਰੋ: file-size `cap` ਨੂੰ ਮੁੜ 1000
   (ਜਾਂ 800), ਕਵਰੇਜ ਦੀਆਂ ਘੱਟੋ-ਘੱਟ ਹੱਦਾਂ +5, ਅਤੇ ਮੋਡੀਊਲਰਾਈਜ਼ ਕੀਤੇ ਪੈਕੇਜਾਂ ਲਈ dead exports 0 ਕਰੋ।

## ਰੈਚਟ ਬੇਸਲਾਈਨ (`quality-baseline.json`)

ਰੈਚਟ ਇੰਜਣ (`scripts/quality/check-quality-ratchet.mjs`) `quality-baseline.json` ਨੂੰ ਪੜ੍ਹਦਾ ਹੈ
ਅਤੇ ਇਸਦੀ ਤੁਲਨਾ ਹੁਣੇ ਇਕੱਤਰ ਕੀਤੀ `quality-metrics.json` ਨਾਲ ਕਰਦਾ ਹੈ। ਕੋਈ ਵੀ ਮੈਟ੍ਰਿਕ ਜੋ ਆਪਣੇ
ਐਪਸਿਲਾਨ ਤੋਂ ਵੱਧ ਪਿੱਛੇ ਜਾਂਦਾ ਹੈ, ਬਿਲਡ ਨੂੰ ਅਸਫਲ ਕਰ ਦਿੰਦਾ ਹੈ।

ਵਰਤਮਾਨ ਵਿੱਚ ਟਰੈਕ ਕੀਤੇ ਜਾਂਦੇ ਮੈਟ੍ਰਿਕ:

| ਮੈਟ੍ਰਿਕ               | ਦਿਸ਼ਾ  | ਅਰਥ                                        |
| --------------------- | ------ | ------------------------------------------ |
| `eslintWarnings`      | `down` | ESLint ਚੇਤਾਵਨੀਆਂ ਦੀ ਗਿਣਤੀ ਵਧਣੀ ਨਹੀਂ ਚਾਹੀਦੀ |
| `coverage.statements` | `up`   | ਸਟੇਟਮੈਂਟ ਕਵਰੇਜ ਘਟਣੀ ਨਹੀਂ ਚਾਹੀਦੀ            |
| `coverage.lines`      | `up`   | ਲਾਈਨ ਕਵਰੇਜ ਘਟਣੀ ਨਹੀਂ ਚਾਹੀਦੀ                |
| `coverage.functions`  | `up`   | ਫੰਕਸ਼ਨ ਕਵਰੇਜ ਘਟਣੀ ਨਹੀਂ ਚਾਹੀਦੀ              |
| `coverage.branches`   | `up`   | ਬ੍ਰਾਂਚ ਕਵਰੇਜ ਘਟਣੀ ਨਹੀਂ ਚਾਹੀਦੀ              |

ਕਿਸੇ ਅਸਲ ਸੁਧਾਰ ਤੋਂ ਬਾਅਦ ਬੇਸਲਾਈਨ ਅੱਪਡੇਟ ਕਰਨ ਲਈ:


`--update` ਫਲੈਗ ਮੌਜੂਦਾ ਮਾਪੇ ਹੋਏ ਮੁੱਲਾਂ ਨੂੰ `quality-baseline.json` ਵਿੱਚ ਲਿਖਦਾ ਹੈ।
ਇਸ ਫ਼ਾਈਲ ਨੂੰ ਉਸ ਤਬਦੀਲੀ ਦੇ ਨਾਲ ਹੀ ਕਮਿਟ ਕਰੋ ਜਿਸ ਨੇ ਮੈਟ੍ਰਿਕ ਵਿੱਚ ਸੁਧਾਰ ਕੀਤਾ ਹੈ। ਬੇਸਲਾਈਨ
ਅੱਪਡੇਟ ਕੀਤੇ ਬਿਨਾਂ ਕਿਸੇ ਮੈਟ੍ਰਿਕ ਨੂੰ ਸੁਧਾਰਨ ਵਾਲੀ PR ਨੂੰ `--require-tighten` ਪਕੜ ਲਵੇਗਾ
(ਪੜਾਅ 6A.5, ਲਾਗੂਕਰਨ ਬਕਾਇਆ ਹੈ)।

### CodeQL ਰੈਚਟ: ਰਿਫ੍ਰੈਸ਼ ਦੀ ਆਵਿਰਤੀ ਅਤੇ ਮੈਨੁਅਲ ਟ੍ਰਿਗਰ

`check:codeql-ratchet` **ਰਿਪੋਜ਼ਟਰੀ ਦੀ ਸਥਿਤੀ ਪੜ੍ਹਦਾ ਹੈ, ਜੋ ਇੱਕ ਸਮਾਂ-ਸੂਚੀ ਅਨੁਸਾਰ ਰਿਫ੍ਰੈਸ਼ ਹੁੰਦੀ ਹੈ — ਹਰ PR ਲਈ ਨਹੀਂ।**
`gh api repos/diegosouzapw/OmniRoute/code-scanning/default-setup` ਵੱਲੋਂ ਰਿਪੋਰਟ ਕੀਤਾ ਜਾਂਦਾ ਹੈ:
`state: configured`, `schedule: weekly`: ਇਹ GitHub ਦਾ ਡਿਫਾਲਟ-ਸੈੱਟਅੱਪ ਸਕੈਨ ਹੈ, ਨਾ ਕਿ ਹਰ ਪੁਸ਼
ਲਈ ਕੀਤਾ ਜਾਣ ਵਾਲਾ ਵਿਸ਼ਲੇਸ਼ਣ। ਨਤੀਜਾ: ਅਲਰਟ ਠੀਕ ਕਰਨ ਵਾਲੀ PR ਦੇ ਮਰਜ ਹੋਣ ਤੋਂ ਬਾਅਦ, ਰੈਚਟ
ਅਗਲਾ ਨਿਰਧਾਰਤ ਸਕੈਨ ਚੱਲਣ ਤੱਕ ਪੁਰਾਣੀ, ਵੱਧ ਗਿਣਤੀ ਹੀ ਪੜ੍ਹਦਾ ਰਹਿੰਦਾ ਹੈ — ਇਸ ਲਈ ਸਕੈਨ ਦੇ
ਅੱਪਡੇਟ ਹੋਣ ਤੱਕ ਇਹ ਹਰ ਖੁੱਲ੍ਹੀ PR, ਫਿਕਸ ਕਰਨ ਵਾਲੀ PR ਦੀਆਂ ਆਪਣੀਆਂ ਅਗਲੀਆਂ ਤਬਦੀਲੀਆਂ ਸਮੇਤ,
'ਤੇ ਰਿਗ੍ਰੈਸ਼ਨ ਰਿਪੋਰਟ ਕਰਦਾ ਹੈ।

**ਮੈਨੁਅਲ ਰਿਫ੍ਰੈਸ਼**: `gh workflow run codeql.yml --ref release/vX.Y.Z` ਵਿਸ਼ਲੇਸ਼ਣ ਨੂੰ ਮੁੜ
ਚਲਾਉਂਦਾ ਹੈ ਅਤੇ ਕੁਝ ਮਿੰਟਾਂ ਵਿੱਚ ਅਲਰਟ ਦੁਬਾਰਾ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਦਾ ਹੈ। ਪਹਿਲਾਂ `.github/workflows/codeql.yml`
ਪੜ੍ਹੋ — ਇਸਦਾ ਸਿਰਲੇਖ ਸਮਝਾਉਂਦਾ ਹੈ ਕਿ ਇਹ ਸਿਰਫ਼ `workflow_dispatch` ਲਈ ਹੈ, **ਕਿਉਂਕਿ ਇਸਦਾ
GitHub ਦੇ "default setup" ਨਾਲ ਟਕਰਾਅ ਹੁੰਦਾ ਹੈ** (`CodeQL analyses from advanced configurations cannot be
processed when the default setup is enabled`)। `push`/`pull_request`/
`schedule` ਟ੍ਰਿਗਰਾਂ ਨੂੰ ਮੁੜ ਬਹਾਲ ਕਰਨ ਲਈ ਪਹਿਲਾਂ **ਮਾਲਕ ਵੱਲੋਂ ਕਾਰਵਾਈ** ਲੋੜੀਂਦੀ ਹੈ: Settings → Code security →
CodeQL: Default → Advanced। ਇਹ ਸਵਿੱਚ ਕੀਤੇ ਬਿਨਾਂ `schedule:` ਟ੍ਰਿਗਰ ਨਾ ਜੋੜੋ — ਇਹ
ਸਿਰਫ਼ ਅਸਫਲ ਰਨ ਹੀ ਪੈਦਾ ਕਰੇਗਾ।

**ਗਿਣਤੀ ਘਟਣ ਤੋਂ ਬਾਅਦ ਬੇਸਲਾਈਨ ਨੂੰ ਕੱਸੋ** — `node scripts/check/check-codeql-ratchet.mjs
--update` ਨਵੀਂ ਮਾਪੀ ਗਿਣਤੀ ਨੂੰ `quality-baseline.json` →
`metrics.codeqlAlerts.value` ਵਿੱਚ ਲਿਖਦਾ ਹੈ, ਤਾਂ ਜੋ ਰੈਚਟ ਚੁੱਪਚਾਪ ਪੁਰਾਣੀ ਉੱਪਰੀ ਸੀਮਾ ਤੱਕ
ਮੁੜ ਰਿਗ੍ਰੈਸ਼ਨ ਦੀ ਆਗਿਆ ਨਾ ਦੇਵੇ। ਕਾਰਜਸ਼ੀਲ ਉਦਾਹਰਨ (2026-09-02/03): PR #12502 ਨੇ 7 ਅਸਲ ਅਲਰਟ
ਠੀਕ ਕੀਤੇ (ਮਾਪੇ ਗਏ ਖੁੱਲ੍ਹੇ ਅਲਰਟ 13 → 6); PR #12530 ਨੇ ਮੇਲ ਕਰਨ ਲਈ ਜਮੀ ਹੋਈ ਬੇਸਲਾਈਨ ਨੂੰ
11 → 6 ਤੱਕ ਕੱਸਿਆ; ਫਿਰ ਬਾਕੀ 6 ਨੂੰ ਹਰ ਅਲਰਟ ਲਈ ਵੱਖਰੇ ਜਾਇਜ਼ੇ ਨਾਲ ਖਾਰਜ ਕਰਕੇ ਖੁੱਲ੍ਹੇ ਅਲਰਟਾਂ
ਦੀ ਗਿਣਤੀ 0 ਕਰ ਦਿੱਤੀ ਗਈ।

**ਖਾਰਜ ਕਰਨਾ ਆਪਰੇਟਰ ਦਾ ਫ਼ੈਸਲਾ ਹੈ (ਸਖ਼ਤ ਨਿਯਮ #14)** — ਖਾਰਜ ਕਰਨ ਵਾਲੀ ਟਿੱਪਣੀ ਵਿੱਚ
ਤਕਨੀਕੀ ਜਾਇਜ਼ਾ ਦਰਜ ਕੀਤੇ ਬਿਨਾਂ ਕਦੇ ਵੀ CodeQL ਅਲਰਟ ਨੂੰ ਖਾਰਜ ਨਾ ਕਰੋ: ਕਿਸੇ ਅੱਪਸਟ੍ਰੀਮ-ਪ੍ਰੋਟੋਕੋਲ
ਲੋੜ ਲਈ `won't fix`, ਕਿਸੇ ਟੈਸਟ ਫਿਕਸਚਰ ਲਈ `used in tests`, ਅਤੇ ਅਜਿਹੇ ਸੈਨਿਟਾਈਜ਼ਰ ਲਈ
`false positive` ਜਿਸਨੂੰ CodeQL ਨਹੀਂ ਦੇਖ ਸਕਦਾ (ਪਿਛਲੀ ਮਿਸਾਲ: `docs/security/ERROR_SANITIZATION.md`)।

3. ਉਲੰਘਣਾ ਠੀਕ ਕਰਨ ਵਾਲੇ ਉਸੇ PR ਵਿੱਚ ਐਂਟਰੀ ਹਟਾਓ — ਇੱਕ ਪੁਰਾਣੀ ਐਂਟਰੀ ਜੋ ਹੁਣ

   ਲਾਗੂ ਹੋਣ ਤੋਂ ਬਾਅਦ, ਇਕੱਲੀ ਰਹਿ ਗਈ ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਐਂਟਰੀ ਕਾਰਨ ਗੇਟ ਨੂੰ ਅਸਫਲ ਕਰ ਦੇਵੇਗੀ)।

ਟੈਸਟਾਂ ਨੂੰ ਤੇਜ਼ੀ ਨਾਲ ਪਾਸ ਕਰਵਾਉਣ ਲਈ ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਵਿੱਚ ਐਂਟਰੀਆਂ **ਨਾ** ਜੋੜੋ। ਵਧਦੀ ਹੋਈ
ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਵਾਲਾ ਹਰਾ ਗੇਟ ਗੁਣਵੱਤਾ ਦਾ ਝੂਠਾ ਭਰੋਸਾ ਦਿੰਦਾ ਹੈ।

### ਜਦੋਂ ਤੁਹਾਡੇ PR ਉੱਤੇ ਕੋਈ ਗੇਟ ਅਸਫਲ ਹੁੰਦਾ ਹੈ

1. **ਗੇਟ ਦਾ ਆਉਟਪੁੱਟ ਧਿਆਨ ਨਾਲ ਪੜ੍ਹੋ** — ਇਹ ਤੁਹਾਨੂੰ ਬਿਲਕੁਲ ਦੱਸਦਾ ਹੈ ਕਿ ਕਿਹੜੀ ਫ਼ਾਈਲ ਜਾਂ ਚਿੰਨ੍ਹ ਨੇ
   ਨਿਯਮ ਦੀ ਉਲੰਘਣਾ ਕੀਤੀ ਹੈ।
2. **ਉਲੰਘਣਾ ਠੀਕ ਕਰੋ** — ਜ਼ਿਆਦਾਤਰ ਗੇਟ ਨਿਰਧਾਰਿਤ ਫ਼ਾਈਲ-ਸਿਸਟਮ ਜਾਂਚਾਂ ਹਨ ਜੋ ਕੋਡ ਦੇ ਸਹੀ ਹੁੰਦਿਆਂ ਹੀ
   ਪਾਸ ਹੋ ਜਾਂਦੇ ਹਨ।
3. **ਜੇ ਉਲੰਘਣਾ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ ਹੈ** (ਅਰਥਾਤ, ਤੁਸੀਂ ਇਸਨੂੰ ਪੈਦਾ ਨਹੀਂ ਕੀਤਾ ਪਰ ਹੁਣ ਗੇਟ
   ਇਸਨੂੰ ਕਵਰ ਕਰਦਾ ਹੈ): ਕਾਰਨ ਦੱਸਦੀ ਟਿੱਪਣੀ ਅਤੇ ਟ੍ਰੈਕਿੰਗ ਮੁੱਦੇ ਦੇ ਨਾਲ ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਵਿੱਚ ਇੱਕ ਐਂਟਰੀ ਸ਼ਾਮਲ ਕਰੋ।
4. **ਜੇ ਗੇਟ ਇੱਕ ਰੈਚਿਟ ਹੈ** (ਕਵਰੇਜ, ESLint ਚੇਤਾਵਨੀਆਂ, ਦੁਹਰਾਵਾ, ਜਟਿਲਤਾ):
   ਤੁਹਾਡੀ ਤਬਦੀਲੀ ਨੇ ਮਾਪਦੰਡ ਨੂੰ ਹੋਰ ਖ਼ਰਾਬ ਕੀਤਾ ਹੈ। ਮੂਲ ਸਮੱਸਿਆ ਨੂੰ ਠੀਕ ਕਰੋ, ਜਾਂ (ਕਦੇ-ਕਦਾਈਂ), ਜੇ ਤਬਦੀਲੀ ਜਾਣਬੁੱਝ ਕੇ ਕੀਤੀ ਗਈ ਹੈ ਅਤੇ ਮਾਪਦੰਡ ਵਿੱਚ
   ਗਿਰਾਵਟ ਸਵੀਕਾਰਯੋਗ ਹੈ, ਤਾਂ `npm run quality:ratchet -- --update` ਚਲਾਓ — ਪਰ PR ਦੇ ਵੇਰਵੇ ਵਿੱਚ ਕਾਰਨ ਦਰਜ ਕਰੋ।
5. **ਸਲਾਹਕਾਰ ਗੇਟ** (`continue-on-error: true`) ਸਿਰਫ਼ ਜਾਣਕਾਰੀ ਲਈ ਹਨ — ਇਹ
   ਮਰਜ ਨੂੰ ਨਹੀਂ ਰੋਕਦੇ ਪਰ CI ਸੰਖੇਪ ਵਿੱਚ ਦਿਖਾਈ ਦਿੰਦੇ ਹਨ। ਫਿਰ ਵੀ ਇਨ੍ਹਾਂ ਨੂੰ ਠੀਕ ਕਰੋ।

## ਨਵਾਂ ਗੇਟ ਸ਼ਾਮਲ ਕਰਨਾ

1. `scripts/check/check-<name>.mjs` (ਜਾਂ `.ts`) ਬਣਾਓ। ਨੀਤੀ ਗੇਟ 0/1 ਨਾਲ ਬੰਦ ਹੁੰਦੇ ਹਨ।
   ਰੈਚਿਟ-ਸ਼ੈਲੀ ਗੇਟ `collect-metrics.mjs` ਰਾਹੀਂ `quality-metrics.json` ਵਿੱਚ ਇੱਕ ਮਾਪਦੰਡ ਲਿਖਦੇ ਹਨ।
2. `package.json` ਵਿੱਚ `"check:<name>": "node scripts/check/check-<name>.mjs"` ਸ਼ਾਮਲ ਕਰੋ।
3. ਇਸਨੂੰ `.github/workflows/ci.yml` ਵਿੱਚ ਢੁਕਵੀਂ ਜੌਬ ਹੇਠ ਜੋੜੋ
   (ਨੀਤੀ → `lint` ਜਾਂ `docs-sync-strict`; ਰੈਚਿਟ → `quality-gate`)।
4. ਜੇ ਇਸਦੀ ਕੋਈ ਮਨਜ਼ੂਰਸ਼ੁਦਾ-ਸੂਚੀ ਹੈ, ਤਾਂ `scripts/check/lib/allowlist.mjs` ਤੋਂ
   `reportStaleEntries()` ਲਾਗੂ ਕਰੋ, ਤਾਂ ਜੋ ਪੁਰਾਣੀਆਂ ਐਂਟਰੀਆਂ ਆਪਣੇ ਆਪ ਪਛਾਣੀਆਂ ਜਾਣ।
5. ਗੇਟ ਦੀ ਪਛਾਣ ਤਰਕ ਨੂੰ ਕਵਰ ਕਰਨ ਵਾਲਾ ਇੱਕ ਟੈਸਟ `tests/unit/build/` ਵਿੱਚ ਲਿਖੋ।
6. ਇਸ ਦਸਤਾਵੇਜ਼ ਨੂੰ ਅੱਪਡੇਟ ਕਰੋ (ਸੰਬੰਧਿਤ ਜੌਬ ਸਾਰਣੀ ਵਿੱਚ ਇੱਕ ਕਤਾਰ ਸ਼ਾਮਲ ਕਰੋ)।

ਇਸ ਸੂਚੀ ਦਾ 2026-06-17 ਨੂੰ `ci.yml` ਨਾਲ ਮਿਲਾਨ ਕੀਤਾ ਗਿਆ ਸੀ (ਪਿਛਲੇ ਸੰਸਕਰਣ ਵਿੱਚ
`audit:deps`, `check:tracked-artifacts`, `check:lockfile`, `check:licenses`,

ਬਦਲਾਅ ਹਨ; ਫਲਿਪ/ਡ੍ਰਾਪ ਨੀਤੀਗਤ ਫੈਸਲੇ ਹਨ ਜੋ ਓਪਰੇਟਰ ਲਈ ਰਾਖਵੇਂ ਹਨ।** ਹੇਠਾਂ ਦਿੱਤਾ ਕੁਝ ਵੀ

(markdownlint + Vale, ਪੂਰੀ ਜੌਬ `continue-on-error`) ਅਤੇ ਵੱਖਰੇ ਸਕੈਨਰ ਵਰਕਫ਼ਲੋ

`quality-baseline.json` ਵਿੱਚ ਹੈ ਪਰ `ci.yml` ਵਿੱਚ ਕਿਸੇ ਬਲੌਕਿੰਗ ਰੈਚਿਟ ਨਾਲ ਜੋੜਿਆ ਨਹੀਂ ਗਿਆ — ਇਹ ਮੈਟ੍ਰਿਕ
ਇਸ ਵੇਲੇ ਅਨਾਥ ਹੈ।

### ਮਰਜ / ਡੀਡੁਪ (ਮਕੈਨੀਕਲ, ਘੱਟ ਜੋਖਮ)

ਹਰ ਉਮੀਦਵਾਰ ਨੂੰ 2026-06-17 ਨੂੰ ਲਾਈਵ ਗੇਟ ਸਥਿਤੀ ਦੇ ਮੁਕਾਬਲੇ ਪ੍ਰਮਾਣਿਤ ਕੀਤਾ ਗਿਆ ਸੀ (ਭਰੋਸਾ ਕਰੋ, ਪਰ ਤਸਦੀਕ ਵੀ ਕਰੋ);
ਕਈ "ਸਪਸ਼ਟ" ਮਰਜਾਂ ਦੇ ਪਿੱਛੇ ਕਰਜ਼ਾ ਲੁਕਿਆ ਹੋਇਆ ਨਿਕਲਿਆ ਅਤੇ ਉਹ **ਸਿੱਧੇ ਤੌਰ 'ਤੇ ਵਰਤਣਯੋਗ ਬਦਲ ਨਹੀਂ** ਹਨ।

- **`check:docs-sync` ਦੋ ਵਾਰ ਚੱਲਦਾ ਹੈ** — `lint` ਜੌਬ ਵਿੱਚ ਵੱਖਰੇ ਤੌਰ 'ਤੇ ਅਤੇ ਮੁੜ `check:docs-all` (`docs-sync-strict`) ਅਤੇ husky pre-commit ਹੁੱਕ ਦੇ ਅੰਦਰ। ✅ **ਪੂਰਾ ਹੋਇਆ** — ਵੱਖਰਾ `lint` ਇਨਵੋਕੇਸ਼ਨ ਹਟਾਇਆ ਗਿਆ।
- **CVE ਸਕੈਨਿੰਗ** — ❌ **ਸਾਫ਼-ਸੁਥਰਾ ਮਰਜ ਨਹੀਂ ਹੈ।** `audit:deps` ਕਿਸੇ ਵੀ high/critical CVE 'ਤੇ ਹਾਰਡ-ਫੇਲ ਹੁੰਦਾ ਹੈ; `check:vuln-ratchet` (osv) ਸਿਰਫ਼ ਬੇਸਲਾਈਨ (ਇਸ ਵੇਲੇ 1 MODERATE) ਦੇ ਮੁਕਾਬਲੇ ਕਿਸੇ _ਰਿਗ੍ਰੈਸ਼ਨ_ 'ਤੇ ਫੇਲ ਹੁੰਦਾ ਹੈ। ਅਰਥ-ਵਿਹਾਰ ਵੱਖਰੇ ਹਨ — `audit:deps` ਨੂੰ ਹਟਾਉਣ ਨਾਲ ਪੂਰਨ high/critical ਗੇਟ ਖਤਮ ਹੋ ਜਾਵੇਗਾ। ਦੋਵੇਂ ਰੱਖੋ।
- **ਚੱਕਰ ਖੋਜ** — ✅ **ਪੂਰਾ ਹੋਇਆ** (#15159 G-01/G-02)। ਇੱਥੇ ਪੁਰਾਣੇ ਟੈਕਸਟ ਨੇ `check:cycles` ਨੂੰ "ਹਰਾ, ਸੰਭਾਲ ਕੇ ਚੁਣਿਆ" ਗੇਟ ਕਿਹਾ ਸੀ ਅਤੇ ਇਸਨੂੰ ਬਲੌਕਿੰਗ ਰੱਖਣ ਨੂੰ ਇਸ ਆਧਾਰ 'ਤੇ ਜਾਇਜ਼ ਠਹਿਰਾਇਆ ਸੀ ਕਿ `check:circular-deps` (dpdm) ਨੇ 91 ਚੱਕਰ ਰਿਪੋਰਟ ਕੀਤੇ ਸਨ। ਉਹ ਹਰਾ ਦਰਜਾ ਇੱਕ **ਗਲਤ ਹਰਾ ਸੰਕੇਤ** ਸੀ: `check:cycles` ਨੇ 5 ਸਬਡਾਇਰੈਕਟਰੀਆਂ (450 ਫ਼ਾਈਲਾਂ) ਸਕੈਨ ਕੀਤੀਆਂ, ਸਿਰਫ਼ ਸਥਿਰ `import|export … from` ਨਾਲ ਮੇਲ ਕੀਤਾ, ਅਤੇ ਹਰੇਕ `@/` ਅਤੇ `@omniroute/open-sse/` ਸਪੈਸੀਫਾਇਰ ਨੂੰ ਛੱਡ ਦਿੱਤਾ, ਇਸ ਲਈ ਇਹ ਉਹ dynamic-import + alias ਚੱਕਰ ਨਹੀਂ ਦੇਖ ਸਕਿਆ ਜੋ ਰਿਪੋ ਵਿੱਚ ਹਾਵੀ ਸਨ। ਠੀਕ ਕੀਤਾ ਗਿਆ: ਗੇਟ ਹੁਣ `src` + `open-sse` (5023 ਫ਼ਾਈਲਾਂ) ਵਿੱਚੋਂ ਲੰਘਦਾ ਹੈ, TypeScript AST ਤੋਂ ਸਪੈਸੀਫਾਇਰ ਇਕੱਠੇ ਕਰਦਾ ਹੈ (ਇਸ ਲਈ `import("…")` ਗਿਣਿਆ ਜਾਂਦਾ ਹੈ ਅਤੇ type-position `typeof import("…")` ਨਹੀਂ), ਅਤੇ tsconfig `paths` ਨੂੰ ਰਿਜ਼ੌਲਵ ਕਰਦਾ ਹੈ। ਇਹ 0 ਨਹੀਂ, ਸਗੋਂ **14** ਚੱਕਰ ਲੱਭਦਾ ਹੈ। ਕਿਉਂਕਿ ਪਹਿਲਾਂ ਤੋਂ ਮੌਜੂਦ 14 ਚੱਕਰਾਂ ਨੂੰ ਗੇਟ PR ਵਿੱਚ ਠੀਕ ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਦਾ, `check:cycles` ਹੁਣ ਇੱਕ **ਰੈਚਿਟ** ਹੈ (`--ratchet`, `quality-baseline.json` ਵਿੱਚ ਸੀਮਾ `metrics.cycles.value = 14`, `direction: down`) — ਇਹ ਕਿਸੇ ਵੀ _ਰਿਗ੍ਰੈਸ਼ਨ_ ਨੂੰ ਬਲੌਕ ਕਰਦਾ ਹੈ ਅਤੇ ਗਿਣਤੀ ਸਿਰਫ਼ ਘਟ ਸਕਦੀ ਹੈ। CI `npm run check:cycles:ratchet` ਚਲਾਉਂਦਾ ਹੈ। ਘਟਾਓ ਦਾ ਕੰਮ **A-01** ਦੇ ਨਾਲ ਚੱਲੇਗਾ। `check:circular-deps` (dpdm) ਵਿਆਪਕ ਦੂਜੀ ਰਾਏ ਵਜੋਂ ਸਲਾਹਕਾਰੀ ਰਹਿੰਦਾ ਹੈ।
- **ਜਟਿਲਤਾ** — ✅ **ਪੂਰਾ ਹੋਇਆ** (`check:complexity-ratchets` / `eslint.complexity-ratchets.config.mjs`): ਇੱਕ ESLint ਵਾਕ, `ruleId` ਮੁਤਾਬਕ ਗਿਣਤੀ ਤਾਂ ਜੋ cyclomatic+max-lines ਅਤੇ cognitive ਬੇਸਲਾਈਨਾਂ ਸੁਤੰਤਰ ਰਹਿਣ; ਵੱਖਰੇ `check:complexity` / `check:cognitive-complexity` ਲੋਕਲ `--update` ਲਈ ਬਰਕਰਾਰ ਹਨ।
- **`/api` ਐਂਟੀ-ਹੈਲੂਸੀਨੇਸ਼ਨ** — ✅ **ਪੂਰਾ ਹੋਇਆ** (`check:api-docs-refs` + `scripts/check/lib/apiRoutes.mjs`): `src/app/api` ਦੀ ਇੱਕ FS ਇਨਵੈਂਟਰੀ, openapi-routes + docs-symbols ਹਾਲੇ ਵੀ ਸੁਤੰਤਰ ਤੌਰ 'ਤੇ ਰਿਪੋਰਟ ਕਰਦੇ ਹਨ; ਵੱਖਰੇ ਚੈਕ ਲੋਕਲ ਰਨਾਂ ਲਈ ਬਰਕਰਾਰ ਹਨ।
