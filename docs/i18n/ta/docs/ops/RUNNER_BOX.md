சுயமாக ஹோஸ்ட் செய்யப்பட்ட pool **.113** இயந்திரத்தில் (`tomni-proxmox-113`) இயங்குகிறது. 2026-10-18 முதல் ஒவ்வொரு
OmniRoute runner-க்கும் **ஒரே ஒரு role**, ஒரு label, மற்றும் அதன் workload-ல் அளவிடப்பட்ட தேவைக்கேற்ற memory/CPU வரம்பு
உள்ளது. Turbopack slot-க்கு build-க்குத் தேவையான வளங்கள் வழங்கப்படுகின்றன; மற்ற slot-கள் அவற்றின்
அளவிடப்பட்ட உச்சநிலைகளுக்கு ஏற்ப ஒதுக்கப்பட்டுள்ளன. Turbopack build, Release-Green
webpack build மற்றும் lint job ஆகியவை ஒரே நேரத்தில் நிகழும்போது மட்டுமே இயந்திரம் அளவுக்கு அதிகமாக வளங்களை ஒதுக்குகிறது;
host swap (16 GB) அதைத் தாங்குகிறது. pull-request Build-கள் hosted runner-களில் இயங்குவதால்,

உள்ளன (முந்தைய மதிப்புகள் `override.conf.bak-20261018` ஆக வைக்கப்பட்டுள்ளன), மேலும் அவை
`systemctl set-property --runtime … MemoryHigh=… MemoryMax=… CPUQuota=…` மூலம் இயங்கிக்கொண்டிருக்கும்போதே செயல்படுத்தப்பட்டன — restart செய்யப்படவில்லை; எனவே
இயங்கிக்கொண்டிருந்த எந்த job-மும் பாதிக்கப்படவில்லை. Label-கள் runners API வழியாக மாற்றப்படுகின்றன
(`gh api -X DELETE repos/<repo>/actions/runners/<id>/labels/<label>` /
`gh api -X POST repos/<repo>/actions/runners/<id>/labels -f 'labels[]=<label>'`), இதுவும் இயங்கிக்கொண்டிருக்கும்போதே செய்யப்படுகிறது.

## janitor-ஐ நிறுவுதல் (ஒருமுறை மட்டும், கணினியில்)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root): ஒவ்வொரு 30 நிமிடங்களுக்கும், /var/log/runner-janitor.log-இல் பதிவுசெய்யவும்
*/30 * * * * MAX_ACTIVE_RUNNERS=6 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

`lsof` அவசியம்: ஒரு பாதையை அகற்றுவதற்கு முன், திறந்திருக்கும் கோப்புகளின் ஒரே
snapshot மூலம் அது செயலற்ற நிலையில் இருப்பதை janitor உறுதிப்படுத்துகிறது; இந்தக் கருவி
இல்லாவிட்டால், அது எதையும் அகற்றாமல் அதைக் குறிப்பிட்டு வெளியேறும்
(exit 1). எந்த மாற்றத்தையும் முதலில் `--dry-run` உடன் முயற்சிக்கவும் — அது என்ன
செய்யவிருக்கிறது என்பதைத் துல்லியமாக அச்சிடும்; எதையும் மாற்றாது.

ஒவ்வொரு இயக்கத்திலும் இது செய்வது: **tmpfs-இல் 3 மணிநேரத்திற்குப்** பிறகும், வட்டிலுள்ள
`_work/_temp`-இல் 24 மணிநேரத்திற்குப் பிறகும் எங்களுடைய எஞ்சியவற்றை (`runner-*`, `omniroute-*`,
`next-build*`, `e2e-build.tar.gz`) அகற்றுகிறது; 75 நிமிடங்களுக்கு மேற்பட்ட `next-build`-ஐ
நிறுத்துகிறது (எந்த job-உம் அவ்வளவு நேரம் இயங்காது — 2026-08-27 அன்று, GitHub அதன் job
தொலைந்துவிட்டதாக அறிவித்த பிறகும் ஒன்று 70 நிமிடங்கள் இயங்கியது); unit **stopped** நிலையில்
உள்ள runners-இன் 48 மணிநேரம் பழைய checkouts-ஐ அகற்றுகிறது; வட்டு பயன்பாடு ≥ 85 %,
memory PSI `full/avg60` ≥ 10 %, மற்றும் listeners எண்ணிக்கை `MAX_ACTIVE_RUNNERS`-ஐவிட
அதிகமாக இருக்கும்போது (omniroute/other பிரிவுடன்) எச்சரிக்கிறது. Exit 1 = கவனம் தேவை;
பதிவைப் படிக்கவும்.

GitHub ஏற்கெனவே கைவிட்டுவிட்ட job-இன் build-ஐ 75 நிமிட விதி கண்டறியாது.
`Runner.Listener` தனது job-ஐப் புதுப்பிக்க முடியாதபோது, `_diag/Runner_*.log`-இல்
`POST request to …/renewjob timed out after 100 seconds` எனக் காட்டப்படும்; கடைசியாக
வெற்றிகரமாகப் புதுப்பிக்கப்பட்ட சுமார் பத்து நிமிடங்களுக்குப் பிறகு, API அந்த job-ஐ `completed`
(failure) எனத் தெரிவிக்கும்; எந்த job-உம் இணைக்கப்படாமல் `next-build` தொடர்ந்து இயங்கும்
(2026-10-18: #17066-இன் Build 19:43 மணிக்கு தோல்வியடைந்தது; ஐந்து நிமிடங்களுக்குப் பிறகும்
அதன் build 40 GB-ஐப் பிடித்துக் கொண்டிருந்தது). சமீபத்திய `_diag/Worker_*.log`-இல் உள்ள
ref-ஐ உறுதிப்படுத்திய பிறகு, PID மூலம் build tree-க்கு மட்டும் SIGTERM அனுப்பவும் —
`next-build`, `npm run build`, `build-next-isolated.mjs` மற்றும் `_work` workers.
`Runner.Listener`, `RunnerService.js` அல்லது `Runner.Worker`-ஐ ஒருபோதும் தொட வேண்டாம்:
worker அந்த job ரத்துசெய்யப்பட்டதாகத் தெரிவிக்கும்; listener தானாகவே மீண்டும் online-க்கு
வரும்.

## ரன்னர் யூனிட்டுகள்: KillMode

ரன்னரின் இயல்புநிலை `KillMode=process`, ஒரு யூனிட் நிறுத்தப்படும்போதோ மறுதொடக்கம் செய்யப்படும்போதோ `Runner.Worker → npm → next-build`-ஐ
இயங்கிக்கொண்டிருக்க விட்டுவிடுகிறது — எந்த ஜாப்புடனும் இணைக்கப்படாத ஓர் அனாதை பில்ட் தொடர்ந்து RAM மற்றும்
CPU-ஐப் பயன்படுத்திக்கொண்டிருக்கும். ஒவ்வொரு OmniRoute யூனிட்டிலும்
(`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)
என்ற drop-in, `KillMode=mixed` உடன் உள்ளது: முதலில் listener-க்கு SIGTERM, பின்னர்
`TimeoutStop`-இல் முழு cgroup-க்கும் SIGKILL. யூனிட்டின் அடுத்த மறுதொடக்கத்தில் இது நடைமுறைக்கு வரும் — **ஒரு நேரத்தில் ஒரு ரன்னரை மட்டும்,
அது idle-ஆக இருக்கும்போது மட்டும்** மறுதொடக்கம் செய்யவும்; idle சரிபார்ப்பையும் மறுதொடக்கத்தையும் ஒரே command-இல் செய்யவும்.
