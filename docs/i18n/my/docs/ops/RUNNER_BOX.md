သတ်မှတ်ထားပါသည်။ Turbopack slot ကို build အတွက် လိုအပ်သည့် resource ပမာဏ ပေးထားပြီး၊ အခြား slot များကို ၎င်းတို့၏
တိုင်းတာရရှိထားသည့် အမြင့်ဆုံးအသုံးပြုမှုနှင့်အညီ သတ်မှတ်ထားပါသည်။ Turbopack build တစ်ခု၊ Release-Green
webpack build တစ်ခုနှင့် lint job တစ်ခု တစ်ချိန်တည်း တိုက်ဆိုင်သည့်အခါမှသာ စက်၏ resource ကို overcommit လုပ်ပါသည်။

## janitor ကို ထည့်သွင်းခြင်း (စက်ပေါ်တွင် တစ်ကြိမ်သာ)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root) - မိနစ် 30 တိုင်း လုပ်ဆောင်ပြီး /var/log/runner-janitor.log သို့ မှတ်တမ်းတင်ရန်
*/30 * * * * MAX_ACTIVE_RUNNERS=6 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

`lsof` လိုအပ်သည်။ janitor သည် လမ်းကြောင်းတစ်ခုကို ဖယ်ရှားခြင်းမပြုမီ ဖွင့်ထားသော
ဖိုင်များ၏ snapshot တစ်ခုဖြင့် ထိုလမ်းကြောင်းကို အသုံးမပြုတော့ကြောင်း သက်သေပြသည်။ ဤ tool
မရှိပါက မည်သည့်အရာကိုမျှ မဖယ်ရှားဘဲ ထိုအကြောင်းကို အသိပေးမည်
(exit 1)။ ပြောင်းလဲမှုတိုင်းကို `--dry-run` ဖြင့် ဦးစွာ စမ်းသပ်ပါ — ၎င်းသည်
လုပ်ဆောင်မည့်အရာကို အတိအကျ ဖော်ပြပေးပြီး မည်သည့်အရာကိုမျှ ပြောင်းလဲထိတွေ့မည်မဟုတ်ပါ။

run တစ်ကြိမ်စီတွင် လုပ်ဆောင်သည့်အရာများမှာ— **tmpfs တွင် 3 h** ကျော်ပြီးနောက်နှင့် disk ရှိ
`_work/_temp` တွင် 24 h ကျော်ပြီးနောက် ကိုယ်ပိုင်ကျန်ရှိဖိုင်များ (`runner-*`, `omniroute-*`,
`next-build*`, `e2e-build.tar.gz`) ကို ရှင်းလင်းသည်။ 75 min ထက်ကြာနေသော
`next-build` ကို ရပ်တန့်သည် (မည်သည့် job မျှ ထိုမျှကြာအောင် မလုပ်ဆောင်ပါ — GitHub က
၎င်း၏ job ပျောက်ဆုံးသွားပြီဟု သတ်မှတ်ပြီးနောက် 2026-08-27 တွင် တစ်ခုသည် 70 min ကြာအောင်
ဆက်လက်လုပ်ဆောင်ခဲ့သည်)။ unit **ရပ်တန့်ထားသော** runner များ၏ 48 h သက်တမ်းရှိ
checkout များကို ရှင်းလင်းသည်။ disk အသုံးပြုမှု ≥ 85 %၊ memory PSI
`full/avg60` ≥ 10 % နှင့် listener အရေအတွက်သည် `MAX_ACTIVE_RUNNERS` ထက်များနေပါက
(omniroute/အခြားဟူ၍ ခွဲခြမ်းဖော်ပြလျက်) သတိပေးသည်။ Exit 1 = အာရုံစိုက်ဖြေရှင်းရန်
လိုအပ်သည်။ log ကို ဖတ်ပါ။

75-minute စည်းမျဉ်းသည် GitHub က လက်လျှော့ပြီးဖြစ်သော job တစ်ခု၏ build ကို မဖမ်းမိနိုင်ပါ။
`Runner.Listener` က ၎င်း၏ job ကို သက်တမ်းမတိုးနိုင်သည့်အခါ `_diag/Runner_*.log` တွင်
`POST request to …/renewjob timed out after 100 seconds` ဟု ပြသသည်။ နောက်ဆုံးအကြိမ်
သက်တမ်းတိုးခြင်း အောင်မြင်ပြီးနောက် ဆယ်မိနစ်ခန့်အကြာတွင် API က job ကို `completed`
(failure) ဟု ဖော်ပြသော်လည်း `next-build` သည် ချိတ်ဆက်ထားသော job မရှိဘဲ ဆက်လက်
လုပ်ဆောင်နေသည် (2026-10-18 တွင် #17066 ၏ Build သည် 19:43 ၌ မအောင်မြင်ကြောင်း
သတ်မှတ်ခံခဲ့ရပြီး ငါးမိနစ်အကြာတွင် ၎င်း၏ build က 40 GB ကို ဆက်လက်သိမ်းယူထားဆဲဖြစ်သည်)။
နောက်ဆုံး `_diag/Worker_*.log` ထဲရှိ ref ကို အတည်ပြုပြီးနောက် PID ဖြင့် build tree ကိုသာ
SIGTERM ပို့ပါ — `next-build`, `npm run build`, `build-next-isolated.mjs` နှင့်
`_work` worker များ။ `Runner.Listener`, `RunnerService.js` သို့မဟုတ် `Runner.Worker`
တို့ကို လုံးဝ မထိပါနှင့်။ worker က job ကို cancelled ဖြစ်ကြောင်း သတင်းပို့ပြီး listener သည်

## Runner ယူနစ်များ: KillMode

Runner ၏ ပုံသေ `KillMode=process` သည် ယူနစ်တစ်ခုကို ရပ်တန့်ခြင်း သို့မဟုတ် ပြန်လည်စတင်ခြင်း ပြုလုပ်သည့်အခါ `Runner.Worker → npm → next-build` ကို ဆက်လက်အသက်ဝင်နေစေသည် — ထို့ကြောင့် မည်သည့် job နှင့်မျှ ချိတ်ဆက်ထားခြင်းမရှိသော orphan build တစ်ခုက RAM နှင့် CPU ကို ဆက်လက်သုံးစွဲနေမည်ဖြစ်သည်။ OmniRoute ယူနစ်တိုင်းတွင် `KillMode=mixed` ပါဝင်သော drop-in
(`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)
ရှိသည်။ ၎င်းက listener ထံသို့ ပထမဦးစွာ SIGTERM ပို့ပြီး `TimeoutStop` ရောက်သည့်အခါ cgroup တစ်ခုလုံးထံသို့ SIGKILL ပို့သည်။ ၎င်းသည် ယူနစ်၏ နောက်တစ်ကြိမ် ပြန်လည်စတင်မှုတွင် အကျိုးသက်ရောက်မည် — **တစ်ကြိမ်လျှင် runner တစ်ခုသာ၊ idle ဖြစ်နေချိန်တွင်သာ** ပြန်လည်စတင်ပြီး idle စစ်ဆေးမှုနှင့် ပြန်လည်စတင်မှုကို command တစ်ခုတည်းအတွင်း လုပ်ဆောင်ပါ။
