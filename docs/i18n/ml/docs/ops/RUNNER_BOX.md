സ്വയം ഹോസ്റ്റ് ചെയ്ത പൂൾ **.113** മെഷീനിലാണ് (`tomni-proxmox-113`) പ്രവർത്തിക്കുന്നത്. 2026-10-18 മുതൽ ഓരോ
OmniRoute റണ്ണറിനും **ഒരു ചുമതല**, ഒരു ലേബൽ, അതിന്റെ വർക്ക്ലോഡിൽ അളന്ന ആവശ്യത്തിനനുസരിച്ചുള്ള മെമ്മറി/CPU ബജറ്റ്
എന്നിവയുണ്ട്. Turbopack സ്ലോട്ടിന് ബിൽഡിന് ആവശ്യമായ വിഭവങ്ങൾ ലഭിക്കുന്നു; മറ്റ് സ്ലോട്ടുകളുടെ വലുപ്പം അവയിൽ
അളന്ന പരമാവധി ഉപയോഗത്തിനനുസരിച്ചാണ്. ഒരു Turbopack ബിൽഡ്, ഒരു Release-Green
webpack ബിൽഡ്, ഒരു lint ജോബ് എന്നിവ ഒരേസമയം വരുമ്പോൾ മാത്രമാണ് മെഷീൻ അതിന്റെ ശേഷിയിലധികം അനുവദിക്കുന്നത്;
ഹോസ്റ്റ് swap (16 GB) അത് കൈകാര്യം ചെയ്യുന്നു. പുൾ-റിക്വസ്റ്റ് Builds ഹോസ്റ്റ് ചെയ്ത പരിതസ്ഥിതിയിൽ പ്രവർത്തിക്കുന്നതിനാൽ,

`systemctl set-property --runtime … MemoryHigh=… MemoryMax=… CPUQuota=…` ഉപയോഗിച്ച് പ്രവർത്തനത്തിനിടയിൽ തന്നെ പ്രയോഗിച്ചു — restart ചെയ്തിട്ടില്ല, അതിനാൽ
പ്രവർത്തിച്ചുകൊണ്ടിരുന്ന ഒരു ജോബിനെയും ബാധിച്ചില്ല. runners API വഴിയാണ് ലേബലുകൾ മാറ്റുന്നത്
(`gh api -X DELETE repos/<repo>/actions/runners/<id>/labels/<label>` /
`gh api -X POST repos/<repo>/actions/runners/<id>/labels -f 'labels[]=<label>'`); ഇതും പ്രവർത്തനത്തിനിടയിൽ തന്നെയാണ് ചെയ്യുന്നത്.

## janitor ഇൻസ്റ്റാൾ ചെയ്യുക (ഒറ്റത്തവണ, മെഷീനിൽ)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root): ഓരോ 30 മിനിറ്റിലും, /var/log/runner-janitor.log-ലേക്ക് ലോഗ് ചെയ്യുക
*/30 * * * * MAX_ACTIVE_RUNNERS=6 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

`lsof` ആവശ്യമാണ്: ഒരു പാത നീക്കംചെയ്യുന്നതിന് മുമ്പ്, തുറന്നിരിക്കുന്ന ഫയലുകളുടെ ഒരു സ്നാപ്പ്ഷോട്ട് ഉപയോഗിച്ച് അത് നിഷ്ക്രിയമാണെന്ന് janitor ഉറപ്പാക്കുന്നു; ഈ ടൂൾ ഇല്ലെങ്കിൽ അത് ഒന്നും നീക്കംചെയ്യാതെ അക്കാര്യം അറിയിക്കുകയും ചെയ്യും (exit 1). ഏത് മാറ്റവും ആദ്യം `--dry-run` ഉപയോഗിച്ച് പരീക്ഷിക്കുക — അത് എന്ത് ചെയ്യുമെന്നത് കൃത്യമായി പ്രിന്റ് ചെയ്യുകയും ഒന്നിലും മാറ്റം വരുത്താതിരിക്കുകയും ചെയ്യും.

ഓരോ റണ്ണിലും ഇത് ചെയ്യുന്നത്: **tmpfs-ൽ 3 മണിക്കൂറും**, ഡിസ്കിലെ `_work/_temp`-ൽ 24 മണിക്കൂറും കഴിഞ്ഞ നമ്മുടെ സ്വന്തം അവശിഷ്ടങ്ങൾ (`runner-*`, `omniroute-*`, `next-build*`, `e2e-build.tar.gz`) നീക്കംചെയ്യുന്നു; 75 മിനിറ്റിലധികം പഴക്കമുള്ള `next-build` അവസാനിപ്പിക്കുന്നു (ഒരു ജോലിയും അത്ര നേരം പ്രവർത്തിക്കാറില്ല — 2026-08-27-ന് GitHub അതിന്റെ ജോലി നഷ്ടപ്പെട്ടതായി പ്രഖ്യാപിച്ചതിന് ശേഷം ഒരെണ്ണം 70 മിനിറ്റ് പ്രവർത്തിച്ചു); യൂണിറ്റ് **നിർത്തിയിരിക്കുന്ന** runners-ന്റെ 48 മണിക്കൂർ പഴക്കമുള്ള checkouts നീക്കംചെയ്യുന്നു; ഡിസ്ക് ഉപയോഗം ≥ 85 %, memory PSI `full/avg60` ≥ 10 %, കൂടാതെ listeners-ന്റെ എണ്ണം `MAX_ACTIVE_RUNNERS`-നേക്കാൾ കൂടുതലാകൽ എന്നിവയെക്കുറിച്ച് മുന്നറിയിപ്പ് നൽകുന്നു (omniroute/മറ്റുള്ളവ എന്ന വേർതിരിച്ച കണക്കോടുകൂടി). Exit 1 = ശ്രദ്ധ ആവശ്യമാണ്; ലോഗ് വായിക്കുക.

## റണ്ണർ യൂണിറ്റുകൾ: KillMode

ഒരു യൂണിറ്റ് നിർത്തുകയോ പുനരാരംഭിക്കുകയോ ചെയ്യുമ്പോൾ റണ്ണറിന്റെ ഡിഫോൾട്ട് `KillMode=process`, `Runner.Worker → npm → next-build`
എന്നതിനെ പ്രവർത്തിച്ചുകൊണ്ടിരിക്കാൻ അനുവദിക്കുന്നു — ഒരു ജോലിയുമായും ബന്ധിപ്പിക്കാത്ത അനാഥ ബിൽഡ് RAM-ഉം
CPU-വും ഉപയോഗിച്ചുകൊണ്ടിരിക്കും. ഓരോ OmniRoute യൂണിറ്റിലും
(`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)
എന്ന drop-in ഉണ്ട്; അതിൽ `KillMode=mixed` ആണ്: ആദ്യം listener-ലേക്ക് SIGTERM, തുടർന്ന്
`TimeoutStop`-ൽ മുഴുവൻ cgroup-ലേക്കും SIGKILL. യൂണിറ്റിന്റെ അടുത്ത പുനരാരംഭത്തിൽ ഇത് പ്രാബല്യത്തിൽ വരും — **ഒരു സമയം
ഒരു റണ്ണർ മാത്രം, അത് idle ആയിരിക്കുമ്പോൾ മാത്രം** പുനരാരംഭിക്കുക; idle പരിശോധനയും പുനരാരംഭവും ഒരേ command-ൽ നടത്തണം.

  വൃത്തിയാക്കരുത്.** പരിശോധനയ്ക്കും ഇല്ലാതാക്കലിനുമിടയിൽ ഇടവേളയുള്ള
  check-then-delete നടപടിയാണ് 2026-08-27-ന് പ്രവർത്തിച്ചുകൊണ്ടിരുന്ന ഒരു Build ജോബിന് അതിന്റെ
  `_work` നഷ്ടപ്പെടാൻ കാരണമായത്. ജാനിറ്റർ പരിശോധനയും നീക്കംചെയ്യലും ഒറ്റ ഘട്ടത്തിൽ
  നിർവഹിക്കുന്നു; അത് തന്നെ ചെയ്യാൻ അനുവദിക്കുക.
- റണ്ണർ ഒരു ജോബിന്റെ മധ്യത്തിൽ നിർത്തുന്നത് ജോബ് റദ്ദാക്കുന്നു (തത്സമയം നിരീക്ഷിച്ചത്):
  അതിന്റെ ലിസണറിന് `Runner.Worker` ചൈൽഡ് ഇല്ലാത്തപ്പോൾ മാത്രം `systemctl stop`
  പ്രവർത്തിപ്പിക്കുക — അതും ഒരൊറ്റ കമാൻഡിൽ ചെയ്യുക.
- വർക്ക്ഫ്ലോകൾ ആർട്ടിഫാക്ടുകൾ `/tmp`-ൽ സൂക്ഷിച്ചുവയ്ക്കരുത് (അത് RAM ആണ്).
  `$RUNNER_TEMP`-ലേക്ക് ഡൗൺലോഡ് ചെയ്യുക (ഓരോ റണ്ണറിനും ഡിസ്കിലാണ്) — 1.3 GB
  `next-build` ആർട്ടിഫാക്ട് tmpfs-ൽ എത്താൻ 27–32 മിനിറ്റ് എടുത്തപ്പോൾ, ഡിസ്കിൽ നിന്ന്
  അപ്ലോഡ് ചെയ്യാൻ 2 മിനിറ്റ് മാത്രമാണ് എടുത്തത്.
