## បញ្ជីសារពើភណ្ឌ Gate និងប្រូហ្វាល់ប្រតិបត្តិការ

### ការទទួលយកបេក្ខភាព

Workflow CI និង Quality Gates នីមួយៗបញ្ចេញសាលក្រមដែលមានស្ថិរភាព៖ `Gate / CI` និង
`Gate / Quality`។ គោលការណ៍ទទួលយកដែលមានកំណែរបស់ពួកវារាយការងារ upstream នីមួយៗ
ថាជាការងារចាំបាច់ ឬជាការងារផ្តល់យោបល់។ ការងារចាំបាច់ដែលអាចអនុវត្តបានត្រូវតែជោគជ័យ៖ លទ្ធផល
ដែលបាត់ អ្នកប្រើបានបោះបង់ រំលង កំពុងរង់ចាំ និងមិនស្គាល់ មិនអាចបញ្ជាក់ PASS បានទេ។ ការចាត់ថ្នាក់
docs-only ឬ catalog-only ដែលត្រឹមត្រូវអាចធ្វើឱ្យ lane កូដមួយមិនអាចអនុវត្តបាន;
PR ព្រាងមិនត្រូវបានទទួលយកជាបេក្ខភាពទេ។ ស្លាក `hotfix` មិនលើកលែងតម្រូវការភស្តុតាងឡើយ។

Workflow ទាំងពីរគ្របដណ្តប់ PR និងការ push ទៅកាន់ branch main/release, ការ dispatch ដោយដៃ និង
ព្រឹត្តិការណ៍ merge-group។ Push, dispatch និង merge-group ដំណើរការជម្រើសពេញលេញ។ Fork
និង merge group ប្រើ hosted runner សម្រាប់ការងារដែលជាធម្មតាជ្រើសរើស self-hosted
runner; ត្រូវតែផ្ទៀងផ្ទាត់ថាមានសមត្ថភាព hosted គ្រប់គ្រាន់ មុនពេលដាក់ឱ្យប្រើប្រាស់។

បង្កាន់ដៃ JSON នីមួយៗកំណត់អត្តសញ្ញាណ SHA ដែលបាន check out, workflow run និង attempt។
CLI បដិសេធភាពមិនត្រូវគ្នារវាង checkout/event SHA។ ការធ្វើតេស្ត Workflow ភ្ជាប់សមាជិកភាពគោលការណ៍
ទៅនឹងបញ្ជី `needs` របស់ verdict job ដើម្បីកុំឱ្យ lane ថ្មី ឬ lane ដែលបានដកចេញបាត់ដោយស្ងៀមស្ងាត់។
បង្កាន់ដៃទាំងនេះគ្របដណ្តប់តែ workflow របស់ខ្លួនប៉ុណ្ណោះ មិនមែនការផ្សព្វផ្សាយ ការដាក់ពង្រាយ ឬផ្នែកខាងក្នុង
របស់ advisory scanner ដែលមានស្រាប់នោះទេ។ ការធ្វើឱ្យឈ្មោះ check ទាំងពីរសកម្មក្នុង branch rules គឺជា
ការផ្លាស់ប្តូរផ្នែករដ្ឋបាលដាច់ដោយឡែក; ការបន្ថែមការងារទាំងនេះមិនការពារ branch ដោយខ្លួនឯងទេ។

### បញ្ជីសារពើភណ្ឌការស្កេនឋិតិវន្ត

បញ្ជីសារពើភណ្ឌ npm-alias ដែលមានកំណែ និងសមាជិកភាព static-scan ស្ថិតនៅក្នុង
`config/quality/gate-manifest.json`។ ដំណើរការ `npm run check:gate-manifest` ដើម្បីផ្ទៀងផ្ទាត់
ឈ្មោះ script និង command ពិតប្រាកដជាមួយ `package.json`; ការបន្ថែម ការដកចេញ និង
ភាពប្រែប្រួលនៃ command នឹងធ្វើឱ្យទាំង local hook និងការងារ change-classification ក្នុង CI បរាជ័យ។
Alias មិនមែនជា workflow job, matrix instance ឬ test case ទេ៖ ចំនួនទាំងនេះមិនត្រូវ
បង្ហាញថាអាចជំនួសគ្នាបានឡើយ។

ប្រើ `npm run quality:scan -- --list` ឬ `npm run quality:scan:fast -- --list`
ដើម្បីពិនិត្យ alias ដែលបានជ្រើសរើសដោយមិនប្រតិបត្តិពួកវា។ Runner ហៅ npm
entrypoint ដូច្នេះ runtime របស់វា (រួមទាំង Bun នៅកន្លែងដែលបានកំណត់រចនាសម្ព័ន្ធ) ត្រូវបានរក្សាទុក។
Manifest កត់ត្រា alias ដែលនៅក្រៅប្រូហ្វាល់ទាំងនោះថាត្រូវបានហៅដោយឡែក ហើយ
command ថែទាំត្រូវបានហាមឃាត់ក្នុងប្រូហ្វាល់ស្កេន read-only។

ប្រូហ្វាល់ទាំងនេះគ្របដណ្តប់តែការស្កេនឋិតិវន្តប៉ុណ្ណោះ។ ពួកវាមិនបញ្ជាក់វិញ្ញាបនបត្រលើ product test,
coverage, packaging, external check ឬការទទួលយក release ពេញលេញរបស់បេក្ខភាពឡើយ។
ការទទួលយក Workflow ប្រើ `config/quality/admission-policy.json` ដែលបានភ្ជាប់ និង
`scripts/quality/admission-verdict.mjs`។ ប្រូហ្វាល់ release-observer នៅតែដាច់ដោយឡែក;
ពិនិត្យ check និងបង្កាន់ដៃដែលអាចអនុវត្តបានរបស់វាដោយឯករាជ្យ។ បញ្ជីសារពើភណ្ឌជាអត្ថបទ
ខាងក្រោមគឺជាឯកសារយោង មិនមែនជាភស្តុតាងថា gate ពិតជាបានដំណើរការនោះទេ។

Script ស្ថិតនៅក្រោម `scripts/check/` (policy gate) និង `scripts/quality/` (ratchet engine)។
ប្រភពការពិតរបស់ CI គឺ `.github/workflows/ci.yml`។

### ផ្លូវលឿនរបស់ Release PR (`quality.yml`)

protected branch, dispatch និង merge group។ PR ប្រើការត្រួតពិនិត្យរហ័សដែលត្រងតាម path។ Duplicate
build ដែលបានបិទជាអចិន្ត្រៃយ៍ត្រូវបានដកចេញ; ការត្រួតពិនិត្យ build/package/boot ពិតប្រាកដនៅតែមានក្នុង CI។

  (`scripts/quality/baseline-headroom.mjs`)។ កិច្ចការ `baseline-headroom` ប្រចាំយប់ផ្សព្វផ្សាយ
  តារាងក្នុងសេចក្តីសង្ខេបនៃការដំណើរការ workflow និងផ្ទុកឡើងរបាយការណ៍ JSON/Markdown របស់វាជា
  `baseline-headroom-<run_id>` ដែលត្រូវបានរក្សាទុករយៈពេល 90 ថ្ងៃ។ ជួរដែលមានការព្រមាន និងស្ថានភាពធ្ងន់ធ្ងរ
  កំណត់អត្តសញ្ញាណច្រកដែលស្ថិតក្នុងចម្ងាយ 10% ពីកម្រិតអតិបរមារបស់វា ឬបានលើសវារួចហើយ។ ពិនិត្យរបាយការណ៍ទាំងនេះ
  ជាការព្រមានជាមុនអំពីការប្រើប្រាស់ថវិកាកំណត់; ពិនិត្យកំណត់សម្គាល់ `_rebaseline_*` របស់ច្រកដែលបង្កបញ្ហា។ កិច្ចការនេះលែង
  បង្កើត ឬធ្វើបច្ចុប្បន្នភាព issue អចិន្ត្រៃយ៍ទៀតហើយ; #12149 រក្សាប្រវត្តិរបាយការណ៍ពីមុន។

**របៀបកូដថ្មី (Clean-as-You-Code) — ចាប់តាំងពី 2026-08-30 សម្រាប់តែផ្លូវលឿននៃ PR**

នៅលើព្រឹត្តិការណ៍ `pull_request` ឯកសារ `quality.yml` បញ្ជូន `--base-ref <PR base SHA>` ទៅ `check:file-size`,
`check:complexity-ratchets` និង `check:dead-code`។ សម្រាប់ `check:complexity-ratchets` និង
`check:dead-code` ច្រកប្រៀបធៀប HEAD ជាមួយ merge-base **ដោយកំណត់ត្រឹមឯកសារដែល PR បានកែប្រែ**
(`scripts/check/newCodeMode.mjs`: merge-base ត្រូវបានបង្កើតជារូបរាងក្នុង
`git worktree` បណ្តោះអាសន្ន ESLint/knip ដំណើរការនៅទីនោះ និងលើ HEAD ហើយចំនួនតាមឯកសារត្រូវបានប្រៀបធៀបភាពខុសគ្នា):

- **រារាំង** — PR បានបន្ថែមការបំពាន cyclomatic/cognitive ឬ dead exports ក្នុងឯកសារដែលវាបានកែប្រែ
  (`complexityNewCode=`, `cognitiveComplexityNewCode=`, `deadExportsNewCode=` ក្នុងកំណត់ហេតុ);
- **ការណែនាំ** — ចំនួនសរុបសកលធៀបនឹងខ្សែមូលដ្ឋានដែលបានបង្កក។ ភាពខុសគ្នាដែលបានទទួលបន្តមិនធ្វើឱ្យ
  PR ដែលគ្មានកំហុសបរាជ័យឡើយ; ភាពខុសគ្នានេះត្រូវបានបង្កកឡើងវិញនៅពេលសម្របសម្រួលការចេញផ្សាយ និងត្រូវបានតាមដានដោយកិច្ចការ headroom។

`check:file-size` ប្រើ base ref តាមលក្ខខណ្ឌរបស់វាផ្ទាល់ (`scripts/check/check-file-size.mjs`, #8522):
វាពិនិត្យរាល់ឯកសារប្រភព និងឯកសារតេស្តក្នុងមែកធាង អានចំនួនបន្ទាត់របស់ឯកសារនីមួយៗនៅ PR base
ដោយប្រើ `git show` ហើយធ្វើឱ្យឯកសារបរាជ័យតែនៅពេលវាកើនលើសតម្លៃធំជាងរវាងកម្រិតខ្ពស់បំផុតនៃខ្សែមូលដ្ឋានរបស់វា
(`frozen` / `testFrozen` ឬ `cap` / `testCap` សម្រាប់ឯកសារដែលនៅក្រៅខ្សែមូលដ្ឋាន) និងទំហំរបស់វានៅ base។
ដូច្នេះ ឯកសារដែលបានខុសពីខ្សែមូលដ្ឋានរួចហើយនៅ base មិនធ្វើឱ្យ PR ដែលគ្មានកំហុសបរាជ័យឡើយ។

`check:boundary:ratchet` អនុវត្តច្បាប់ដូចគ្នាចំពោះចំនួនតែមួយរបស់វា
(`scripts/quality/measure-boundary.mjs --ratchet --base-ref <sha>`): នៅលើព្រឹត្តិការណ៍ PR ទាំង fast-gate របស់

វាស់ពីការនាំចេញ `git archive` ហើយ PR បរាជ័យតែនៅពេលចំនួន edge

នៅតែរក្សាកម្រិតអតិបរមាដាច់ខាត ហើយ SHA មូលដ្ឋានដែលមិនអាចដោះស្រាយបាននឹងត្រឡប់ទៅប្រើកម្រិតនេះវិញជាមួយការព្រមាន។

## បន្ទាត់គោល Ratchet (`quality-baseline.json`)

ម៉ាស៊ីន ratchet (`scripts/quality/check-quality-ratchet.mjs`) អាន `quality-baseline.json`
ហើយប្រៀបធៀបវាជាមួយ `quality-metrics.json` ដែលទើបតែបានប្រមូល។ Metric ណាមួយដែលថយចុះ
លើសពី epsilon របស់វា នឹងធ្វើឱ្យ build បរាជ័យ។

Metrics ដែលកំពុងត្រូវបានតាមដាន៖

| Metric                | ទិសដៅ  | អត្ថន័យ                                     |
| --------------------- | ------ | ------------------------------------------- |
| `eslintWarnings`      | `down` | ចំនួនការព្រមាន ESLint មិនត្រូវកើនឡើងទេ      |
| `coverage.statements` | `up`   | Coverage របស់ statement មិនត្រូវធ្លាក់ចុះទេ |
| `coverage.lines`      | `up`   | Coverage របស់បន្ទាត់មិនត្រូវធ្លាក់ចុះទេ     |
| `coverage.functions`  | `up`   | Coverage របស់ function មិនត្រូវធ្លាក់ចុះទេ  |
| `coverage.branches`   | `up`   | Coverage របស់ branch មិនត្រូវធ្លាក់ចុះទេ    |

ដើម្បីធ្វើបច្ចុប្បន្នភាពបន្ទាត់គោល បន្ទាប់ពីមានការកែលម្អពិតប្រាកដ៖

```bash
npm run quality:ratchet -- --update
git add quality-baseline.json
```

### បញ្ចូលគ្នា / លុបភាពស្ទួន (បែបមេកានិច ហានិភ័យទាបជាង)

បេក្ខភាពនីមួយៗត្រូវបានផ្ទៀងផ្ទាត់ជាមួយស្ថានភាព gate ជាក់ស្តែងនៅថ្ងៃទី 2026-06-17 (ទុកចិត្ត ប៉ុន្តែត្រូវផ្ទៀងផ្ទាត់);

- **ការរកឃើញវដ្ត** — ✅ **រួចរាល់** (#15159 G-01/G-02)។ អត្ថបទចាស់នៅទីនេះបានហៅ `check:cycles` ថាជា gate "ពណ៌បៃតង ដែលបានជ្រើសរើសយ៉ាងប្រុងប្រយ័ត្ន" និងបានលើកហេតុផលឱ្យរក្សាវាជា blocking ព្រោះ `check:circular-deps` (dpdm) បានរាយការណ៍វដ្តចំនួន 91។ ស្ថានភាពពណ៌បៃតងនោះគឺជា **ភាពវិជ្ជមានក្លែងក្លាយ**៖ `check:cycles` បានស្កេនថតរងចំនួន 5 (450 files), ផ្គូផ្គងតែ `import|export … from` បែប static ហើយបានបោះបង់រាល់ specifier `@/` និង `@omniroute/open-sse/` ដូច្នេះវាមិនអាចមើលឃើញវដ្ត dynamic-import + alias ដែលមានច្រើនជាងគេក្នុង repo បានទេ។ បានកែរួច៖ ឥឡូវ gate ដើរឆ្លងកាត់ `src` + `open-sse` (5023 files), ប្រមូល specifier ពី TypeScript AST (ដូច្នេះ `import("…")` ត្រូវបានរាប់ ខណៈ `typeof import("…")` នៅទីតាំង type មិនត្រូវបានរាប់) ហើយ resolve `paths` របស់ tsconfig។ វារកឃើញវដ្តចំនួន **14** មិនមែន 0 ទេ។ ដោយសារវដ្តដែលមានស្រាប់ចំនួន 14 មិនអាចត្រូវបានជួសជុលនៅក្នុង gate PR បាន `check:cycles` ឥឡូវនេះគឺជា **ratchet** (`--ratchet`, ពិដាន `metrics.cycles.value = 14` ក្នុង `quality-baseline.json`, `direction: down`) — វារារាំង _ការធ្លាក់ចុះ_ ណាមួយ ហើយចំនួននេះអាចតែថយចុះប៉ុណ្ណោះ។ CI ដំណើរការ `npm run check:cycles:ratchet`។ ការកាត់បន្ថយជាបន្តបន្ទាប់ទៅជាមួយ **A-01**។ `check:circular-deps` (dpdm) នៅតែជាការណែនាំក្នុងនាមជាមតិទីពីរដែលទូលំទូលាយជាង។
