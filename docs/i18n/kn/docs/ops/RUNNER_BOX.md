ಸ್ವಯಂ-ಹೋಸ್ಟ್ ಮಾಡಿದ ಪೂಲ್ **.113** ಯಂತ್ರದಲ್ಲಿ (`tomni-proxmox-113`) ಚಲಿಸುತ್ತದೆ. 2026-10-18 ರಿಂದ ಪ್ರತಿ
OmniRoute ರನ್ನರ್ಗೆ **ಒಂದು ಪಾತ್ರ**, ಒಂದು ಲೇಬಲ್ ಮತ್ತು ಅದರ ವರ್ಕ್ಲೋಡ್ನ ಮಾಪನಗಳಿಗೆ ಅನುಗುಣವಾಗಿ ನಿಗದಿಪಡಿಸಿದ ಮೆಮೊರಿ/CPU ಬಜೆಟ್
ಇದೆ. Turbopack ಸ್ಲಾಟ್ಗೆ ಬಿಲ್ಡ್ಗೆ ಅಗತ್ಯವಿರುವಷ್ಟು ಸಂಪನ್ಮೂಲಗಳು ಸಿಗುತ್ತವೆ; ಇತರ ಸ್ಲಾಟ್ಗಳನ್ನು ಅವುಗಳ
ಮಾಪನ ಮಾಡಿದ ಗರಿಷ್ಠ ಬಳಕೆಗೆ ಅನುಗುಣವಾಗಿ ಗಾತ್ರಗೊಳಿಸಲಾಗಿದೆ. Turbopack ಬಿಲ್ಡ್, Release-Green
webpack ಬಿಲ್ಡ್ ಮತ್ತು lint ಜಾಬ್ ಒಂದೇ ಸಮಯದಲ್ಲಿ ನಡೆದಾಗ ಮಾತ್ರ ಯಂತ್ರವು ತನ್ನ ಸಾಮರ್ಥ್ಯಕ್ಕಿಂತ ಹೆಚ್ಚು ಸಂಪನ್ಮೂಲಗಳನ್ನು ಹಂಚುತ್ತದೆ;
ಹೋಸ್ಟ್ swap (16 GB) ಅದನ್ನು ನಿಭಾಯಿಸುತ್ತದೆ ಮತ್ತು pull-request ಬಿಲ್ಡ್ಗಳು ಹೋಸ್ಟ್ ಮಾಡಿದ ರನ್ನರ್ಗಳಲ್ಲಿ ನಡೆಯುವುದರಿಂದ,
Turbopack ಸ್ಲಾಟ್ ಹೆಚ್ಚಿನ ಸಮಯ ನಿಷ್ಕ್ರಿಯವಾಗಿರುತ್ತದೆ:

(ಹಿಂದಿನ ಮೌಲ್ಯಗಳನ್ನು `override.conf.bak-20261018` ಆಗಿ ಉಳಿಸಲಾಗಿದೆ) ಮತ್ತು ಅವುಗಳನ್ನು
`systemctl set-property --runtime … MemoryHigh=… MemoryMax=… CPUQuota=…` ಮೂಲಕ ಚಾಲನೆಯಲ್ಲಿರುವಾಗಲೇ ಅನ್ವಯಿಸಲಾಗಿದೆ — ಮರುಪ್ರಾರಂಭ ಮಾಡಿಲ್ಲ, ಆದ್ದರಿಂದ
ಚಾಲನೆಯಲ್ಲಿದ್ದ ಯಾವುದೇ ಜಾಬ್ಗೆ ಪರಿಣಾಮವಾಗಿಲ್ಲ. ಲೇಬಲ್ಗಳನ್ನು runners API ಮೂಲಕ
(`gh api -X DELETE repos/<repo>/actions/runners/<id>/labels/<label>` /
`gh api -X POST repos/<repo>/actions/runners/<id>/labels -f 'labels[]=<label>'`) ಬದಲಾಯಿಸಲಾಗುತ್ತದೆ; ಇದನ್ನೂ ಚಾಲನೆಯಲ್ಲಿರುವಾಗಲೇ ಮಾಡಲಾಗುತ್ತದೆ.

## janitor ಅನ್ನು ಸ್ಥಾಪಿಸಿ (ಒಮ್ಮೆ ಮಾತ್ರ, ಯಂತ್ರದಲ್ಲಿ)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root): ಪ್ರತಿ 30 ನಿಮಿಷಕ್ಕೊಮ್ಮೆ, /var/log/runner-janitor.log ಗೆ ಲಾಗ್ ಮಾಡಿ
*/30 * * * * MAX_ACTIVE_RUNNERS=6 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

`lsof` ಅಗತ್ಯವಿದೆ: ಒಂದು ಪಥವನ್ನು ತೆಗೆದುಹಾಕುವ ಮೊದಲು, ತೆರೆದಿರುವ
ಫೈಲ್ಗಳ ಒಂದೇ ಸ್ನ್ಯಾಪ್ಶಾಟ್ ಬಳಸಿ ಅದು ನಿಷ್ಕ್ರಿಯವಾಗಿದೆ ಎಂದು janitor ಖಚಿತಪಡಿಸುತ್ತದೆ; ಈ ಪರಿಕರವಿಲ್ಲದಿದ್ದರೆ
ಅದು ಏನನ್ನೂ ತೆಗೆದುಹಾಕುವುದಿಲ್ಲ ಮತ್ತು ಹಾಗೆಂದು ತಿಳಿಸುತ್ತದೆ
(exit 1). ಯಾವುದೇ ಬದಲಾವಣೆಯನ್ನು ಮೊದಲು `--dry-run` ಬಳಸಿ ಪ್ರಯತ್ನಿಸಿ — ಅದು ತಾನು ನಿಖರವಾಗಿ ಏನು
ಮಾಡಲಿದೆ ಎಂಬುದನ್ನು ಮುದ್ರಿಸುತ್ತದೆ ಮತ್ತು ಯಾವುದನ್ನೂ ಮುಟ್ಟುವುದಿಲ್ಲ.

ಪ್ರತಿ ಚಾಲನೆಯಲ್ಲೂ ಅದು ಮಾಡುವ ಕೆಲಸ: **tmpfs ನಲ್ಲಿ 3 ಗಂ.** ಮತ್ತು ಡಿಸ್ಕ್ನ
`_work/_temp` ನಲ್ಲಿ 24 ಗಂ. ಕಳೆದ ನಂತರ ನಮ್ಮದೇ ಉಳಿಕೆಗಳನ್ನು (`runner-*`, `omniroute-*`,
`next-build*`, `e2e-build.tar.gz`) ಸ್ವಚ್ಛಗೊಳಿಸುತ್ತದೆ; 75 ನಿಮಿಷಕ್ಕಿಂತ ಹಳೆಯದಾದ `next-build` ಅನ್ನು
ಕೊನೆಗೊಳಿಸುತ್ತದೆ (ಯಾವುದೇ ಜಾಬ್ ಅಷ್ಟು ಹೊತ್ತು ನಡೆಯುವುದಿಲ್ಲ — 2026-08-27 ರಂದು GitHub ಅದರ ಜಾಬ್ ಕಳೆದುಹೋಗಿದೆ
ಎಂದು ಘೋಷಿಸಿದ ನಂತರವೂ ಒಂದು ಜಾಬ್ 70 ನಿಮಿಷ ನಡೆಯಿತು); ಯುನಿಟ್ **ನಿಂತಿರುವ** ರನ್ನರ್ಗಳ 48 ಗಂ. ಹಳೆಯ
ಚೆಕ್ಔಟ್ಗಳನ್ನು ತೆಗೆದುಹಾಕುತ್ತದೆ; ಡಿಸ್ಕ್ ≥ 85 %, ಮೆಮೊರಿ PSI
`full/avg60` ≥ 10 %, ಮತ್ತು `MAX_ACTIVE_RUNNERS` ಗಿಂತ ಹೆಚ್ಚು ಲಿಸನರ್ಗಳಿದ್ದರೆ
(omniroute/ಇತರೆ ವಿಭಾಗೀಕರಣದೊಂದಿಗೆ) ಎಚ್ಚರಿಸುತ್ತದೆ. Exit 1 = ಗಮನ ಅಗತ್ಯ; ಲಾಗ್ ಓದಿ.

GitHub ಈಗಾಗಲೇ ಕೈಬಿಟ್ಟಿರುವ ಜಾಬ್ನ ಬಿಲ್ಡ್ ಅನ್ನು 75-ನಿಮಿಷದ ನಿಯಮ ಪತ್ತೆಹಚ್ಚುವುದಿಲ್ಲ.
`Runner.Listener` ತನ್ನ ಜಾಬ್ ಅನ್ನು ನವೀಕರಿಸಲು ಸಾಧ್ಯವಾಗದಾಗ, `_diag/Runner_*.log` ನಲ್ಲಿ
`POST request to …/renewjob timed out after 100 seconds` ಕಾಣಿಸುತ್ತದೆ; ಕೊನೆಯ ಯಶಸ್ವಿ ನವೀಕರಣದ ಸುಮಾರು
ಹತ್ತು ನಿಮಿಷಗಳ ನಂತರ API ಜಾಬ್ ಅನ್ನು `completed` (ವಿಫಲ) ಎಂದು ವರದಿ ಮಾಡುತ್ತದೆ ಮತ್ತು ಯಾವುದೇ ಜಾಬ್
ಲಗತ್ತಿಸದೆ `next-build` ಚಾಲನೆಯಲ್ಲೇ ಇರುತ್ತದೆ (2026-10-18: #17066 ರ ಬಿಲ್ಡ್ 19:43 ಕ್ಕೆ ವಿಫಲವಾಯಿತು
ಮತ್ತು ಐದು ನಿಮಿಷಗಳ ನಂತರವೂ ಅದರ ಬಿಲ್ಡ್ 40 GB ಅನ್ನು ಹಿಡಿದಿಟ್ಟುಕೊಂಡಿತ್ತು). ಅತ್ಯಂತ ಹೊಸ
`_diag/Worker_*.log` ನಲ್ಲಿ ref ಅನ್ನು ದೃಢೀಕರಿಸಿ, ನಂತರ PID ಮೂಲಕ ಬಿಲ್ಡ್ ಟ್ರೀಗೆ ಮಾತ್ರ SIGTERM ಕಳುಹಿಸಿ —
`next-build`, `npm run build`, `build-next-isolated.mjs` ಮತ್ತು `_work` ವರ್ಕರ್ಗಳು.
`Runner.Listener`, `RunnerService.js` ಅಥವಾ `Runner.Worker` ಅನ್ನು ಎಂದಿಗೂ ಮುಟ್ಟಬೇಡಿ: ವರ್ಕರ್
ಜಾಬ್ ಅನ್ನು ರದ್ದುಗೊಳಿಸಲಾಗಿದೆ ಎಂದು ವರದಿ ಮಾಡುತ್ತದೆ ಮತ್ತು ಲಿಸನರ್ ಸ್ವತಃ ಮತ್ತೆ ಆನ್ಲೈನ್ಗೆ ಬರುತ್ತದೆ.

## ರನ್ನರ್ ಯೂನಿಟ್ಗಳು: KillMode

ರನ್ನರ್ನ ಡೀಫಾಲ್ಟ್ `KillMode=process`, ಯೂನಿಟ್ ಅನ್ನು ನಿಲ್ಲಿಸಿದಾಗ ಅಥವಾ ಮರುಪ್ರಾರಂಭಿಸಿದಾಗ `Runner.Worker → npm → next-build`
ಅನ್ನು ಚಾಲನೆಯಲ್ಲೇ ಬಿಡುತ್ತದೆ — ಯಾವುದೇ ಜಾಬ್ಗೆ ಲಗತ್ತಾಗಿರದ ಅನಾಥ ಬಿಲ್ಡ್ RAM ಮತ್ತು
CPU ಅನ್ನು ಬಳಸುತ್ತಲೇ ಇರುತ್ತದೆ. ಪ್ರತಿ OmniRoute ಯೂನಿಟ್ಗೂ
(`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)
ನಲ್ಲಿ `KillMode=mixed` ಇರುವ ಡ್ರಾಪ್-ಇನ್ ಇದೆ: ಮೊದಲು listener ಗೆ SIGTERM, ನಂತರ
`TimeoutStop` ಸಮಯದಲ್ಲಿ ಸಂಪೂರ್ಣ cgroup ಗೆ SIGKILL. ಯೂನಿಟ್ನ ಮುಂದಿನ ಮರುಪ್ರಾರಂಭದಲ್ಲಿ ಇದು
ಜಾರಿಗೆ ಬರುತ್ತದೆ — **ಒಂದು ಸಮಯದಲ್ಲಿ ಒಂದೇ ರನ್ನರ್ ಅನ್ನು, ಅದು ನಿಷ್ಕ್ರಿಯವಾಗಿದ್ದಾಗ ಮಾತ್ರ** ಮರುಪ್ರಾರಂಭಿಸಿ,
ನಿಷ್ಕ್ರಿಯತೆ ಪರಿಶೀಲನೆ ಮತ್ತು ಮರುಪ್ರಾರಂಭ ಎರಡನ್ನೂ ಒಂದೇ ಕಮಾಂಡ್ನಲ್ಲಿ ಮಾಡಿ.
