## janitor انسٹال کریں (صرف ایک بار، مشین پر)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root): ہر 30 منٹ بعد، لاگ /var/log/runner-janitor.log میں لکھیں
*/30 * * * * MAX_ACTIVE_RUNNERS=6 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

`lsof` درکار ہے: janitor کسی راستے کو ہٹانے سے پہلے کھلی فائلوں کے ایک snapshot کے ذریعے ثابت کرتا ہے کہ وہ زیرِ استعمال نہیں، اور اس ٹول کے بغیر یہ کچھ بھی نہیں ہٹاتا اور اس کی وضاحت کرتا ہے
(exit 1)۔ کسی بھی تبدیلی کو پہلے `--dry-run` کے ساتھ آزمائیں — یہ بالکل وہی دکھاتا ہے جو یہ کرے گا
اور کسی چیز کو تبدیل نہیں کرتا۔

ہر بار چلنے پر یہ کیا کرتا ہے: ہماری اپنی باقیات (`runner-*`، `omniroute-*`،
`next-build*`، `e2e-build.tar.gz`) کو **tmpfs پر 3 گھنٹے** اور ڈسک پر موجود
`_work/_temp` میں 24 گھنٹے کے بعد صاف کرتا ہے؛ 75 منٹ سے پرانے `next-build` کو ختم کرتا ہے (کوئی job اتنی دیر نہیں چلتی —
2026-08-27 کو ایک job، GitHub کی جانب سے اسے گم شدہ قرار دینے کے بعد بھی 70 منٹ تک چلتی رہی)؛ ایسے runners کے 48 گھنٹے پرانے
checkouts کو ہٹاتا ہے جن کا unit **رکا ہوا** ہو؛ ڈسک ≥ 85 %، memory PSI
`full/avg60` ≥ 10 %، اور `MAX_ACTIVE_RUNNERS` سے زیادہ listeners ہونے پر تنبیہ کرتا ہے (ساتھ
omniroute/دیگر کی تفصیل بھی دیتا ہے)۔ Exit 1 = توجہ درکار ہے؛ لاگ پڑھیں۔

75 منٹ کا اصول ایسے build کو نہیں پکڑتا جس کی job سے GitHub پہلے ہی دست بردار ہو چکا ہو۔ جب
`Runner.Listener` اپنی job کی تجدید نہیں کر پاتا تو `_diag/Runner_*.log` میں
`POST request to …/renewjob timed out after 100 seconds` دکھائی دیتا ہے، API آخری کامیاب تجدید کے تقریباً دس منٹ بعد job کو `completed`
(failure) بتاتا ہے، اور `next-build` کسی منسلک job کے بغیر چلتا رہتا ہے
(2026-10-18: #17066 کا build 19:43 پر ناکام قرار دیا گیا تھا، اور پانچ منٹ بعد بھی اس کا build
40 GB روکے ہوئے تھا)۔ تازہ ترین `_diag/Worker_*.log` میں ref کی تصدیق کریں، پھر
صرف build tree کو PID کے ذریعے SIGTERM بھیجیں — `next-build`، `npm run build`، `build-next-isolated.mjs` اور
`_work` workers۔ `Runner.Listener`، `RunnerService.js` یا `Runner.Worker` کو کبھی نہ چھیڑیں:
worker job کو cancelled کے طور پر رپورٹ کرتا ہے اور listener خود ہی دوبارہ online ہو جاتا ہے۔

## رنر یونٹس: KillMode

رنر کا ڈیفالٹ `KillMode=process`، یونٹ روکے یا دوبارہ شروع کیے جانے پر بھی `Runner.Worker → npm → next-build`
کو چلتا چھوڑ دیتا ہے — یوں کسی جاب سے منسلک نہ ہونے کے باوجود ایک یتیم بلڈ RAM اور
CPU استعمال کرتا رہتا ہے۔ ہر OmniRoute یونٹ میں ایک ڈراپ اِن
(`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)
موجود ہے جس میں `KillMode=mixed` ہے: پہلے listener کو SIGTERM، پھر
`TimeoutStop` پر پورے cgroup کو SIGKILL۔ یہ یونٹ کے اگلے ریاسٹارٹ پر مؤثر ہوتا ہے — **ایک وقت میں
صرف ایک رنر، اور صرف اس کے idle ہونے پر، دوبارہ شروع کریں**، نیز idle جانچ اور ریاسٹارٹ ایک ہی کمانڈ میں کریں۔

## آپریٹنگ قواعد

- **ایک وقت میں صرف ایک Turbopack build — label کے ذریعے نافذ۔** مکمل Turbopack
  `next build` چلانے والا ہر job `[self-hosted, omni-build]` کو ہدف بناتا ہے، اور صرف **`omniroute-113-5`**
  پر یہ label موجود ہے: `ci.yml` کا `Build`، `npm-publish.yml` کا `publish`، `nightly-v4-build`، `preview-artifact`،
  nightly a11y build (#16853) اور `docker-publish.yml` کا **amd64** (BuildKit کے اندر webpack —
  وہاں Turbopack کریش ہوا تھا، run 33253576569)۔ arm64 Docker مرحلہ `ubuntu-24.04-arm` ہی پر رہتا ہے۔
  `docker-publish` کا amd64، `ci.yml` کے `Build` کے ساتھ `heavy-build-main` concurrency group
  کا اشتراک کرتا ہے (`cancel-in-progress: false`)۔ Docker Engine کا `omniroute-113-5` پر ہونا ضروری ہے۔
  دوسرا Turbopack slot 78 GB میں سما نہیں سکتا (2 × 33–37 GB، علاوہ ازیں مشین کا باقی بوجھ)؛ دوسرا slot صرف
  webpack builds کے لیے محفوظ ہے۔
- **Pull request کے Builds hosted runners پر چلتے ہیں (2026-10-18)۔** `ci.yml` کا `Build` صرف
  `push` اور `workflow_dispatch` کے لیے `omni-build` تک پہنچتا ہے؛ ہر `pull_request` (اپنی origin سے ہو یا fork سے)
  اور `merge_group` کا Build، webpack کے ساتھ `ubuntu-latest` پر چلتا ہے۔ اپنی origin والی ہر PR کو slot کی طرف
  بھیجنے پر، ایک Turbopack Build نے اسے 29–58 منٹ تک مصروف رکھا، 18 Builds زیادہ سے زیادہ 18 گھنٹے تک قطار میں رہے،
  اور release line کے اپنے push Build کو 40 jobs میں صرف ایک مرتبہ slot ملا۔ Hosted runner پر یہی PR Build،
  PR کے دوسرے jobs کے ساتھ 8–12 منٹ لیتا ہے۔ Turbopack، یعنی وہ bundler جسے `npm-publish` شائع کرتا ہے،
  release line پر default branch کے nightly a11y build (04:41 UTC)، slot تک پہنچنے والے ہر push یا dispatch Build،
  اور خود `npm-publish` کے ذریعے بدستور استعمال اور جانچا جاتا ہے۔ `tests/unit/build/heavy-build-queue.test.ts`
  چار شقوں والے gate کو مقید رکھتا ہے۔
- **Turbopack slot کو کبھی اس کی پیمائش شدہ ضرورت سے کم نہ کریں۔** 2026-10-18 کو 18:06 پر slot کو
  `omni-release` کے لیے جگہ بنانے کی خاطر 56G/60G سے گھٹا کر 40G/44G کیا گیا۔ compile مرحلہ اپنی پوری مدت میں
  `MemoryHigh` پر اٹکا رہا (memory PSI `full` 30–43 %)، اور اسی cgroup کا اشتراک کرنے والا `Runner.Listener`
  اپنے job کی تجدید نہ کر سکا۔ 2026-10-17 کی مالک کی مقرر کردہ 56G/60G حد اسی دن بحال کر دی گئی۔
  اس قدر سے نیچے build ناکام نہیں ہوتا؛ وہ شدید thrashing کا شکار ہوتا ہے، اور job ضائع ہو جاتا ہے۔
- **Release-Green کا اپنا slot ہے (2026-10-18)۔** اس وقت تک دونوں Release-Green validations
  `omni-build` پر چلتے تھے: ہر push پر (~10/hour، ایک دن میں 100 push runs میں سے 97 کام کے دوران منسوخ ہوئے)
  اور روزانہ تین مکمل ~2 h sweeps (05:29 والا sweep slot کے لیے 6 h منتظر رہا) — واحد build
  slot اپنی گنجائش سے کئی گنا زیادہ زیرِ استعمال تھا اور اپنی origin والے PR Builds گھنٹوں انتظار کرتے تھے۔
  `release-green` اور `main-green` اب `OMNIROUTE_USE_TURBOPACK=0` کے ساتھ `omni-release`
  (صرف `omniroute-113-6`) کو ہدف بناتے ہیں، اور شروع ہو جانے والا run اب کسی نئے push کے باعث منسوخ نہیں ہوتا
  (زیرِ انتظار slot اب بھی jobs کے طوفان کو یکجا کر دیتا ہے)۔ `tests/unit/build/runner-capacity-routing.test.ts`
  routing، webpack switch، اور اس بات کو مقید رکھتا ہے کہ `omni-release` پر کوئی بھی چیز Turbopack کے ساتھ build نہ ہو۔
- **ہلکا pool: `omni-light`۔** `omniroute-113` اور `omniroute-113-2` وہ nightly jobs چلاتے ہیں جنہیں
  صرف backend والا `next build` (~5–6 GB؛ webpack) اور `quality.yml` کا `lint-guard` درکار ہوتا ہے۔ `omniroute-113`
