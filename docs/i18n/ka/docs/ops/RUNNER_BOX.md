## janitor-ის დაყენება (ერთჯერადად, სერვერზე)

```bash
scp scripts/ops/runner-janitor.sh root@192.168.0.113:/opt/omniroute-ops/runner-janitor.sh
ssh root@192.168.0.113 'chmod +x /opt/omniroute-ops/runner-janitor.sh; apt-get install -y lsof'
# cron (root): ყოველ 30 წუთში, ჟურნალის ჩაწერა /var/log/runner-janitor.log-ში
*/30 * * * * MAX_ACTIVE_RUNNERS=6 /opt/omniroute-ops/runner-janitor.sh >> /var/log/runner-janitor.log 2>&1
```

`lsof` აუცილებელია: წაშლამდე janitor ღია ფაილების ერთი მომენტალური სურათით ამოწმებს, რომ ბილიკი უმოქმედოა; ამ ხელსაწყოს გარეშე ის არაფერს შლის და ამის შესახებ გაცნობებთ (exit 1). ნებისმიერი ცვლილება ჯერ `--dry-run`-ით მოსინჯეთ — ის ზუსტად აჩვენებს, რას გააკეთებდა, და არაფერს ცვლის.

რას აკეთებს ყოველი გაშვებისას: ასუფთავებს ჩვენსავე ნარჩენებს (`runner-*`, `omniroute-*`, `next-build*`, `e2e-build.tar.gz`) **tmpfs-ზე 3 სთ-ის**, ხოლო დისკზე, `_work/_temp`-ში — 24 სთ-ის შემდეგ; აჩერებს 75 წუთზე ძველ `next-build`-ს (არცერთი დავალება ამდენ ხანს არ სრულდება — 2026-08-27-ს ერთი მათგანი 70 წუთის განმავლობაში მუშაობდა მას შემდეგ, რაც GitHub-მა მისი დავალება დაკარგულად გამოაცხადა); შლის 48 საათის წინანდელ checkout-ებს იმ runner-ებისთვის, რომელთა unit-იც **გაჩერებულია**; გასცემს გაფრთხილებას, როცა დისკის შევსება ≥ 85 %-ია, მეხსიერების PSI `full/avg60` ≥ 10 %-ია, ან მსმენელების რაოდენობა `MAX_ACTIVE_RUNNERS`-ს აღემატება (omniroute/სხვები დაყოფით). Exit 1 = ყურადღებაა საჭირო; წაიკითხეთ ჟურნალი.

75-წუთიანი წესი ვერ აფიქსირებს build-ს, რომლის შესრულებაზეც GitHub-მა უკვე ხელი ჩაიქნია. როცა `Runner.Listener` საკუთარ დავალებას ვეღარ აახლებს, `_diag/Runner_*.log` აჩვენებს `POST request to …/renewjob timed out after 100 seconds`-ს, API დავალებას `completed`-ად (წარუმატებლად) აღნიშნავს ბოლო წარმატებული განახლებიდან დაახლოებით ათი წუთის შემდეგ, ხოლო `next-build` მუშაობას მიმაგრებული დავალების გარეშე აგრძელებს (2026-10-18: #17066-ის build 19:43-ზე წარუმატებლად გამოცხადდა, თუმცა ხუთი წუთის შემდეგ მისი build კვლავ 40 GB-ს იკავებდა). გადაამოწმეთ ref უახლეს `_diag/Worker_*.log`-ში, შემდეგ კი PID-ის მიხედვით SIGTERM მხოლოდ build-ის პროცესების ხეს გაუგზავნეთ — `next-build`, `npm run build`, `build-next-isolated.mjs` და `_work` worker-ები. არასოდეს შეეხოთ `Runner.Listener`-ს, `RunnerService.js`-ს ან `Runner.Worker`-ს: worker დავალებას გაუქმებულად აღნიშნავს, ხოლო listener თავისით ბრუნდება ონლაინ რეჟიმში.

## Runner-ის ერთეულები: KillMode

Runner-ის ნაგულისხმევი `KillMode=process` ერთეულის გაჩერების ან გადატვირთვისას `Runner.Worker → npm → next-build` პროცესებს ცოცხალს ტოვებს — ობლად დარჩენილი build განაგრძობს RAM-ისა და CPU-ის მოხმარებას, მიუხედავად იმისა, რომ მასზე მიბმული job აღარ არსებობს. OmniRoute-ის ყველა ერთეულს აქვს drop-in ფაილი
(`/etc/systemd/system/actions.runner.diegosouzapw-OmniRoute.<name>.service.d/10-killmode.conf`)
`KillMode=mixed`-ით: ჯერ SIGTERM ეგზავნება listener-ს, ხოლო `TimeoutStop`-ის დადგომისას SIGKILL — მთელ cgroup-ს. ცვლილება ძალაში შევა ერთეულის შემდეგი გადატვირთვისას — გადატვირთეთ **ერთ ჯერზე მხოლოდ ერთი runner და მხოლოდ მაშინ, როცა ის უქმეა**, უქმეობის შემოწმება და გადატვირთვა კი ერთსა და იმავე ბრძანებაში შეასრულეთ.
